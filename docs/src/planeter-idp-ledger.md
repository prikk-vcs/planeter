# planeter — the identity provider ledger (sui-id and any other OpenID Connect provider)

| | |
|---|---|
| Document | What planeter has **measured or been told** about the OpenID Connect provider it prefers, one row per fact, with who said it and what planeter does about it. The twin of `planeter-prikk-dependency-ledger.md` for the provider side (RFC 014 D-12). **Nothing here is a claim about a provider planeter has not tested**; the only sentence the documents may use is "tested with sui-id {version} on {date}", and **since 2026-11-27 it is true for `0.92.0` and for the checks listed in ID-11, with the limits listed there, and for nothing else**. |
| Version | v1.1 (2026-11-27): the interoperability test against the tag `0.92.0` (ID-11, ID-12); v1.0 (2026-11-25): the first reply of the sui-id architect. |
| Rule | A reply from the provider is folded into this ledger **before any code changes**. Every re-read (each planeter release cycle) reads the provider's **`CHANGELOG.md`**, because advisories are disclosed there and not always as a separate notice. A provider release is named in planeter's documents only after its notes were read. |

| ID-1 | **`email_verified` is always `false`** (no verification flow exists; nothing sets the timestamp the claim reads). | sui-id architect, measured in source at `648e2ae`, 2026-11-25 | **MEASURED on `0.92.0`, 2026-11-27 (ID-11)** (first TOLD by the provider) | planeter stores an email **only** when `email_verified` is true, so it stores **none** from sui-id: the correct, safe result; not a bug. |
| ID-2 | **The ID token carries `iss`, `sub`, `aud`, `iat`, `exp`, `nonce`, `jti`, `acr`, `amr`, and `email`/`email_verified` under the `email` scope. It carries no `name` and no `preferred_username`**: those come from the userinfo endpoint. The only ID-token algorithm is **EdDSA**. | same | **MEASURED on `0.92.0`, 2026-11-27 (ID-11)** (first TOLD by the provider) | planeter does **not** read `name` or `preferred_username` at all (RFC 014 amendment 1: the person chooses their own handle and display name); so it makes **no userinfo request**. EdDSA is accepted today. |
| ID-3 | `acr` is `"1"`, `"2"` or `"3"`; `amr` holds `pwd`, `otp`, `hwk`, `mfa`, `fed`. They say **which factors, not when**; an ID token from a refresh echoes the original sign-in's values. | same | **MEASURED on `0.92.0`, 2026-11-27 (ID-11)** (first TOLD by the provider) | not used for recency. Possibly useful later to require a second factor for a `full` token (a question, not a plan). |
| ID-4 | **`prompt`, `max_age` and `auth_time` are not implemented and not scheduled; the authorization request silently ignores them.** A user with a live provider session gets a code with no new sign-in even when `prompt=login` was sent. A sui-id RFC (152, proposed) would honour them and refuse what it cannot. | same | **MEASURED on `0.92.0`, 2026-11-27 (ID-11)** (first TOLD by the provider) | planeter **sends neither parameter** until a tagged release says it honours them (sending would only suggest a guarantee that does not exist), and **never reads a successful response as proof of a recent sign-in**: the page's claim stays "a sign-in to planeter within 15 minutes". |
| ID-5 | No front- or back-channel logout, none scheduled. **Disabling or deleting a user at sui-id revokes their refresh tokens, sessions and pending codes in the same transaction.** The recommended way to notice: a periodic **refresh** (an `invalid_grant` means the person is gone); no `offline_access` needed; a refresh token lasts 14 days by default, rotates on every use with reuse detection, requires the client to be registered with the `refresh_token` grant. | same | **MEASURED on `0.92.0`, 2026-11-27 (ID-11)** (first TOLD by the provider) | **A planeter session outlives the provider's.** Until a refresh check exists (RFC 014 open question 7, the owner's), planeter makes the session lifetime configurable (`PLANETER_SESSION_HOURS`, RFC 014 amendment 1) and the documents tell the operator to **disable a person in both places**. |
| ID-6 | `sub` is a random UUID v4, 36 lowercase hyphenated characters, fixed at creation, **never reused** (a deleted user stays as a deleted row). `preferred_username` has no character or length rule for an administrator-created user and no rename path; `name` has no length bound. | same | **MEASURED on `0.92.0`, 2026-11-27 (ID-11)** (first TOLD by the provider) | planeter stores `sub` as the identity (with the issuer); everything else is untrusted text (and is not read: ID-2). |
| ID-7 | The previous signing key **stays in the JWKS until an administrator deletes it**; the JWKS carries `Cache-Control: public, max-age=300`; **a new key is published at the moment it becomes the signer, not before** (an RFC would publish the next key early). | same | **MEASURED on `0.92.0`, 2026-11-27 (ID-11)** (first TOLD by the provider) | planeter's one JWKS refresh on an unknown `kid` is right, **and must be sent with `Cache-Control: no-cache`** so that a shared cache cannot answer it with the stale copy (RFC 014 amendment 1; a handoff). |
| ID-8 | Nothing is under a stability promise before 1.0; the endpoints, `S256`, `EdDSA` and the claims above have not changed in a long time and a change would be named in the `CHANGELOG.md` of its release. Advisories: private reports; fixes disclosed in the `CHANGELOG.md` of the release that carries them; a GitHub advisory only sometimes. A production-readiness milestone with a soak test has not started; no date. | same | TOLD | read the provider's `CHANGELOG.md` at each re-read; name a release only after reading its notes; never call it production-ready. |
| ID-9 | An embeddable module: the **contract** exists (RFC 119, accepted 2026-11-01, no code); the work is not written or scheduled. The sui-id architect will propose to its owner a clause that an embedding which exposes OIDC endpoints passes the **same conformance suite** as the standalone sui-id (a proposal, not a promise). | same | TOLD | planeter does not embed an identity provider (RFC 014 D-1); no action. |
| ID-10 | **The interoperability test must run against a tagged release, not a commit; two items are added to the plan:** send `prompt=login` and check that planeter does not treat the result as a recent sign-in; disable the test user at sui-id and check that the next refresh fails and the planeter session ends (**if planeter has no refresh check, the test reports what it does have: the session continues until its lifetime, measured**). | same | **DONE 2026-11-27 (ID-11)** | the interoperability handoff (RFC 014 D-12). |
| ID-11 | **The interoperability test, measured (2026-11-27): planeter's own provider code (the real `OidcProvider`, the real `curl`, the one-host egress guard) against a real sui-id built from the tag `0.92.0` (commit `45cb6a49…`, Rust 1.95, release profile), in process, behind a TLS stand-in with a throw-away CA. Nine checks, 48 facts, all 48 confirm what ID-1…ID-7 said (0 corrected).** Discovery (`issuer` exact, endpoints on the issuer's authority, `["EdDSA"]`, PKCE `["S256"]`, `client_secret_basic`/`post`/`none`; document 1,037 B, no `Cache-Control`; key set 161 B with one Ed25519 key, `public, max-age=300`); the code flow with PKCE S256 for a public and a confidential client (secret by Basic); the ID token's exact claim set `acr, amr, aud, email, email_verified, exp, iat, iss, jti, nonce, sub` (no `name`, no `preferred_username`; `email`/`email_verified` absent for a user without an email); `sub` a lowercase hyphenated UUID v4, **the same on a second sign-in**; `email_verified` **false**; a replayed code, a code after 60 s (waited 65), a wrong verifier (it also spends the code) refused; planeter refuses a wrong or replayed `state`, a code from another flow and a wrong `nonce`; **`prompt=login&max_age=0` with a live provider session returns a code at once, no `auth_time`** (planeter sends neither); after a key rotation every earlier key stays and the new one is there at once, and a sign-in signed by the new key succeeds through planeter's one `no-cache` refresh and **fails without it** behind a cache that serves the old set; a provider slow (15.0 s bound), down, stopped (SIGSTOP), answering garbage or another issuer: an error and no principal, never a hang, always under 25 s; **offboarding: a planeter session made before the user was disabled stays valid until its lifetime; planeter's part 30 ms**. **Limits (they travel with the sentence):** a local build of the tag, **in process** (the server's handlers, cookies and the confined `curl` were not exercised: the product has no private CA, RFC 014 open question 4), a throw-away CA and a TLS stand-in; **not shown**: `sub` never reused after deletion, the other `acr`/`amr` values (no second factor was enrolled), "a new key is published not before it becomes the signer", the stability promise, the embeddable module. | sui-id test report `sui-id-interop-review-request.md`, evidence `sui-id-interop-logs/` (one file per check, the provider's request log) | **MEASURED** (ID-1…ID-7 now measured on `0.92.0`; ID-8, ID-9 not things a test shows; ID-10 done) | `docs/accounts.md` may say **"planeter's sign-in code was tested with sui-id 0.92.0 on 2026-11-27"** (the longer wording is the page's and the document test's) with exactly these checks and limits beside it, and nothing about any other release or about `main` |
| ID-12 | **Three things that differ from what planeter had assumed (none from the ledger; reproductions, not security claims; sent to the sui-id architect in the letter of 2026-11-27):** (1) the first-run commands in sui-id's `main` documents (`sui-id init`, `config sample`, `admin registration-token issue`) **do not exist in the `0.92.0` binary** (it has `--print-sample-config` and `admin issue-registration-token`); (2) **the console's "Confidential client" box does nothing when unchecked** (an absent form field is read as `true`: `unwrap_or(true)`), so a public client cannot be created from the console as its Quick Start says; (3) **`POST /admin/login` is limited to 10 a minute per client address** (behind a proxy not in `trusted_proxies` every user shares one).
