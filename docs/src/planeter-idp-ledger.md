# planeter — the identity provider ledger (sui-id and any other OpenID Connect provider)

| | |
|---|---|
| Document | What planeter has **measured or been told** about the OpenID Connect provider it prefers, one row per fact, with who said it and what planeter does about it. The twin of `planeter-prikk-dependency-ledger.md` for the provider side (RFC 014 D-12). **Nothing here is a claim about a provider planeter has not tested**; the only sentence the documents may use is "tested with sui-id {version} on {date}" and none is true yet. |
| Version | v1.0 (2026-11-25): the first reply of the sui-id architect. |
| Rule | A reply from the provider is folded into this ledger **before any code changes**. Every re-read (each planeter release cycle) reads the provider's **`CHANGELOG.md`**, because advisories are disclosed there and not always as a separate notice. A provider release is named in planeter's documents only after its notes were read. |

| ID | Fact | Source | Status | What planeter does |
|---|---|---|---|---|
| ID-1 | **`email_verified` is always `false`** (no verification flow exists; nothing sets the timestamp the claim reads). | sui-id architect, measured in source at `648e2ae`, 2026-11-25 | TOLD (not yet measured by planeter) | planeter stores an email **only** when `email_verified` is true, so it stores **none** from sui-id: the correct, safe result; not a bug. |
| ID-2 | **The ID token carries `iss`, `sub`, `aud`, `iat`, `exp`, `nonce`, `jti`, `acr`, `amr`, and `email`/`email_verified` under the `email` scope. It carries no `name` and no `preferred_username`**: those come from the userinfo endpoint. The only ID-token algorithm is **EdDSA**. | same | TOLD | planeter does **not** read `name` or `preferred_username` at all (RFC 014 amendment 1: the person chooses their own handle and display name); so it makes **no userinfo request**. EdDSA is accepted today. |
| ID-3 | `acr` is `"1"`, `"2"` or `"3"`; `amr` holds `pwd`, `otp`, `hwk`, `mfa`, `fed`. They say **which factors, not when**; an ID token from a refresh echoes the original sign-in's values. | same | TOLD | not used for recency. Possibly useful later to require a second factor for a `full` token (a question, not a plan). |
| ID-4 | **`prompt`, `max_age` and `auth_time` are not implemented and not scheduled; the authorization request silently ignores them.** A user with a live provider session gets a code with no new sign-in even when `prompt=login` was sent. A sui-id RFC (152, proposed) would honour them and refuse what it cannot. | same | TOLD | planeter **sends neither parameter** until a tagged release says it honours them (sending would only suggest a guarantee that does not exist), and **never reads a successful response as proof of a recent sign-in**: the page's claim stays "a sign-in to planeter within 15 minutes". |
| ID-5 | No front- or back-channel logout, none scheduled. **Disabling or deleting a user at sui-id revokes their refresh tokens, sessions and pending codes in the same transaction.** The recommended way to notice: a periodic **refresh** (an `invalid_grant` means the person is gone); no `offline_access` needed; a refresh token lasts 14 days by default, rotates on every use with reuse detection, requires the client to be registered with the `refresh_token` grant. | same | TOLD | **A planeter session outlives the provider's.** Until a refresh check exists (RFC 014 open question 7, the owner's), planeter makes the session lifetime configurable (`PLANETER_SESSION_HOURS`, RFC 014 amendment 1) and the documents tell the operator to **disable a person in both places**. |
| ID-6 | `sub` is a random UUID v4, 36 lowercase hyphenated characters, fixed at creation, **never reused** (a deleted user stays as a deleted row). `preferred_username` has no character or length rule for an administrator-created user and no rename path; `name` has no length bound. | same | TOLD | planeter stores `sub` as the identity (with the issuer); everything else is untrusted text (and is not read: ID-2). |
| ID-7 | The previous signing key **stays in the JWKS until an administrator deletes it**; the JWKS carries `Cache-Control: public, max-age=300`; **a new key is published at the moment it becomes the signer, not before** (an RFC would publish the next key early). | same | TOLD | planeter's one JWKS refresh on an unknown `kid` is right, **and must be sent with `Cache-Control: no-cache`** so that a shared cache cannot answer it with the stale copy (RFC 014 amendment 1; a handoff). |
| ID-8 | Nothing is under a stability promise before 1.0; the endpoints, `S256`, `EdDSA` and the claims above have not changed in a long time and a change would be named in the `CHANGELOG.md` of its release. Advisories: private reports; fixes disclosed in the `CHANGELOG.md` of the release that carries them; a GitHub advisory only sometimes. A production-readiness milestone with a soak test has not started; no date. | same | TOLD | read the provider's `CHANGELOG.md` at each re-read; name a release only after reading its notes; never call it production-ready. |
| ID-9 | An embeddable module: the **contract** exists (RFC 119, accepted 2026-11-01, no code); the work is not written or scheduled. The sui-id architect will propose to its owner a clause that an embedding which exposes OIDC endpoints passes the **same conformance suite** as the standalone sui-id (a proposal, not a promise). | same | TOLD | planeter does not embed an identity provider (RFC 014 D-1); no action. |
| ID-10 | **The interoperability test must run against a tagged release, not a commit; two items are added to the plan:** send `prompt=login` and check that planeter does not treat the result as a recent sign-in; disable the test user at sui-id and check that the next refresh fails and the planeter session ends (**if planeter has no refresh check, the test reports what it does have: the session continues until its lifetime, measured**). | same | OPEN | the interoperability handoff (RFC 014 D-12). |
