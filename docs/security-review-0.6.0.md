# Security review of the 0.6.0 work

| | |
|---|---|
| Document | The security pass before a release, for what changed since 0.5.0 (`docs/security-review-0.5.0.md` stays as the record of that release). It is a **review by the architect of the design, the code paths and the evidence**, surface by surface — not an external penetration test. 0.6.0 adds no inbound flow, no new action and no new binary; it changes what the server does when a framework or a dependency answers, how it judges a failed write, and which versions of prikk, SQLite and the sanitizer it runs on. |
| Date | 2026-11-14. Basis: the threat model v0.6 (unchanged by 0.6.0: no new surface), the reviews of each part (D-70…D-75), the gates and the rehearsal of the release candidate `9bef01f`. |
| Verdict | **No open finding blocks 0.6.0.** One finding is recorded for after the release (IS-58, below); the residual risks of 0.5.0 stand. |

## How to read the evidence column
*Test* = a test that fails if the control is removed (with a **mutation** run where the dev team showed it failing once); *gate* = a project gate (`cargo deny`, `cargo audit`, ENF-2, `pin-check`, `floor-check`, the boundary check); *measured* = a number from a real prikk or a real rehearsal.

## Surfaces

| Surface | What it defends against | Controls and evidence |
|---|---|---|
| **A failed accept** (`propose`) | answering "refused, nothing was left" when the store had changed (prikk 0.56+ writes the claims last, so a write error leaves `sync pending` unchanged); the opposite error, a hostile member flagging a repository read-only with one bad upload | refused only on **positive evidence**: the pending set **and** a store signature (path, size, mtime of every file under `.prikk`, locks excluded; a bounded `lstat` walk, any failure counts as "changed") equal before and after; every decision-time refusal that leaves the tree untouched (bad signature, truncated artifact, over-limit object) stays *refused* with no flag. *Test* with a real prikk 0.57.0 (read-only claim container → incomplete, flag, intent and artifact kept, recovery converges, a resend records one revision) and the three refusals; *mutation* (the old rule fails the test); *measured*: 80 µs at 5,000 and at 20,000 patches (PK-79) |
| **Recovery** | recovery stopping on output it does not know, or clearing a lock it should not | `doctor`'s unreached-object family is **closed**: `PRIKK-DOCTOR-UNREACHED-CONTENT` (info) and `…-OBJECT` are known, any other `PRIKK-DOCTOR-UNREACHED-*` is unreadable and recovery stops with the text kept; `unlock` is only ever built with `--force` after planeter's own witnesses, never `--yes` (prikk 0.57.0 lets `--yes` clear an `unknown` holder, which is what a sandbox produces): *test* on the recorded argv and a scan of every `src` for `"--yes"`; *mutation* for both |
| **Framework answers** (413, 405, 400, 404 on any address) | an empty or plain-text answer in one language; an answer that tells a stranger whether a repository exists | one edge layer around the router turns each into the project's own answer (`{code, message, hint}` under `/api/`; a page elsewhere); the answers are **route-level and say nothing about whether a repository exists** (*test*: a stranger and a hidden repository get the same answer); the proposal upload and the archive staging keep their own bounds (*test*) |
| **Language negotiation** | a header or cookie used to cause work, or to smuggle markup into a page | `Accept-Language` is matched against the registry only (exact → script → language → none); no header text reaches a page; the cookie is a registered tag or ignored (*test*: the negotiation table, malformed tags, `*`, empty) |
| **The sanitizer** (`ammonia` 4.2.5) | mutation XSS through MathML/SVG integration points (RUSTSEC-2026-0533) | defaults only: 75 allowed tags, none of the ten raw-text tags, neither `math` nor `svg`, so the advisory's precondition does not hold; updated anyway; *test*: the advisory's shape for every raw-text tag and integration point, plain and through Markdown, output inert **and a fixed point**; *mutation* (math and raw-text tags allowed → the test fails) |
| **The database** (`rusqlite` 0.41.1, SQLite 3.54.1) | uninitialised page-cache memory returned for a crafted database with a mismatched `-wal` (RUSTSEC-2026-0459) | updated; planeter opens only the file the operator names (`PLANETER_DB`; no request, upload or archive reaches an open: grep in the dev team's review); *rehearsal*: a database written by the released 0.5.0 opens identically after a clean stop and after a SIGKILL with a `-wal`, and 0.5.0 reads and writes the file the new build wrote (rollback); `PRAGMA integrity_check` ok in every direction. Not covered: large databases, a `-wal` of another page size, power loss |
| **Supply chain** | a known-vulnerable or unexpectedly licensed dependency | `cargo deny check` and `cargo audit` exit 0 with **no ignore** on the candidate (*gate*, a fresh database, 1,509 advisories); one licence added for one crate (Zlib for `foldhash`, an exception like `webpki-roots`); the lock is 214 crates, unchanged in count; the compiler pin 1.99.1 and every `uses:` SHA and the base-image digest were reviewed on 2026-11-14 (table in the review request) |
| **The prikk floor** | a server and a client that cannot work together; a repository format a tool refuses | floor 0.57.0 in the code, `planeter-client`, CI, the release workflow and the Dockerfile (*gate*: `floor-check`); the server refuses to start below it and the client stops at its own message before touching anything (*test*); new repositories are format 8, existing ones keep theirs (the driver never runs `format upgrade`) |
| **The release chain and the image** | shipping an image that cannot start or a different image from the one tested | unchanged from 0.5.0 and re-rehearsed on the candidate (run 43575291310): both architectures built, the image **run** (`planeter 0.6.0`, `prikk 0.57.0`, `bwrap`, `prlimit`), glibc checked, the registry's config digest equal to the run image's, attestations created. I could not verify the rehearsal package's attestation (private package); the release's own will be verified after the push, as for 0.5.0 |
| **Japanese** | a wrong or misleading sentence in a trust label | signed off by the owner twice (2026-10-31 and 2026-11-14; the sign-off is data on the language's row, the baseline says 0 messages newer than it); a rule keeps retired wording out (*test*); the sentence of the one badge that said something untrue was rewritten in the owner's own words |

## What was not done (said plainly)
* Everything of the 0.5.0 list that still holds: **no external penetration test and no fuzzing campaign**; the sandbox is not exercised inside the image in CI; the server's end-to-end tests run on x86_64 only; no second factor (RR-10) and in-memory rate limits (RR-11, RR-13).
* **No person using assistive technology has tried the pages**, in either language (`docs/accessibility.md` says so).
* **The upgrade rehearsal covers small databases.**
* **`sync seal` on a maintainer's machine** costs the square of the claims on a large history until prikk 0.58.0 (PK-82); the forge never seals.

## Findings made on the way, all closed before this review
A write error after the patches were stored was read as "refused" (the 0.56 re-baseline, PK-79); `doctor`'s new code would have stopped recovery on every killed accept (found because the real-prikk test failed); `unlock` printed a line the strict reader refused (same); a badge legend said something untrue after a received import (D3); the framework's own answers bypassed the catalog (0.5.0 period, closed by the edge layer); the `ammonia` and `rusqlite` advisories (updated, no ignore).

## Finding recorded for after the release
**IS-58.** `release.yml` and `supply-chain.yml` install `cargo-deny` and `cargo-audit` at their newest versions (`cargo install … --locked` without `--version`): the two tools that gate a release are not pinned, so a new tool version can change a gate's verdict or, in the worst case, be the vector. Fix: pin both by version (and read their advisories in the pins review), then rehearse. Not done before 0.6.0 because the release chain was just rehearsed on the candidate and the gates passed with the current tools.

## Residual risks accepted
RR-10…RR-18 as in the threat model; the not-done list above.
