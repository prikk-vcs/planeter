## How to read the evidence column
*Test* = a test that fails if the control is removed (with a **mutation** the dev team showed failing once); *gate* = a project gate; *measured* = a number from a real run; *seen* = read in the saved pages and JSON of the end-to-end run.

## Surfaces

| Surface | What it defends against | Controls and evidence |
|---|---|---|
| **The trees of a revision** (rebuilt by prikk in the sandbox, walked by the server) | a symbolic link that makes the server read its own files; a pipe or device that hangs it; a tree that exhausts memory, disk or time | `lstat` decides every entry's type; a link is read as bytes and never opened; only a regular file is opened, and re-checked just before; pipes, devices, sockets are listed and never opened; depth 64, 10,000 entries per tree, a file read only up to 256 KiB (a larger one compared by a streamed hash); the extraction itself is prikk's, bounded by `--max-bytes`/`--max-files` and the sandbox. *Test* on hand-built trees (a link to `/etc/passwd`, to a FIFO, a loop, a 100-level directory, 20,000 changes) and through real prikk; *mutations*: links followed, FIFO opened (it hangs and the harness kills it), no depth cap, no entry cap — all caught |
| **What is shown** (names and diff text) | markup or script in a page; text that hides or reorders what a reviewer reads (bidirectional controls, zero-width, control codes, a very long line); a link that comes from file content | the engine makes every name and line display-safe (invalid bytes, controls, separators, bidirectional controls, zero-width characters become visible escapes; names cut at 1,024 bytes and lines at 2,000 characters, **on a character boundary, with the cut said as data: `path_cut_bytes`, `cut_chars`**, so no English marker lives in the data); the page escapes again (Askama autoescape, no `|safe` in the three templates) and applies its own second look; diff text is text, never HTML, never the sanitizer; no link comes from content (a link target is shown as text). *Test*: markup, `<img onerror>`, a bidi override in a name and a line, zero-width and ESC characters, a 2,500-character line, a `javascript:` target; *mutations*: each of the two escapings removed, a made-up link, the cut count dropped, a name cut inside a character — all caught |
| **Cost** | a hostile or careless reader making the server do unbounded work | the same admission as any `extract` (the heavy pool at 9.5 × the byte bound + 8 MiB = 616 MiB at the defaults, RFC 011); one view at a time per revision (single flight), **at most eight waiters, the ninth refused as busy without parking a thread** (*test*: 20 at once → 9 × 200, 11 × 503 with `Retry-After`, one extraction pair; *mutation*); a 30 s wall; bounded outputs (10,000 files, 5,000 diff lines per file, 2,000 characters per line, 1,024 bytes per name); a **deterministic** bounded diff (an edit-distance cap, then a whole-file replacement flagged `approximate`; `similar` was not adopted because its Myers has no such cap and a cached answer must not depend on timing); a cache keyed by content under the spool (64 MiB, least recently used out), never filled by a transient failure, with a versioned key so an entry of an earlier format is never read (*test*); *measured*: worst-case diff 84 ms, a 1,000-file repository 2.9 s cold and 1.4 ms cached. The HTML proposal pages have no per-address limiter (as the other proposal pages); the admission, the cache and the waiter bound are what limit them (RR-19) |
| **Who may see it** | the view telling a stranger that a repository, proposal, revision or file exists | the routes are in the authorization table and probed; a hidden repository, an unknown proposal, revision or file give one 404, byte for byte (*test*, seven addresses, both pages and JSON); headers equal the proposal page's (`no-store`, `Vary` with `Accept-Language`, `Content-Language`, the CSP) |
| **What the view claims** | a reviewer believing the files are signed or verified | every page says the files are rebuilt from the patches and that nothing here is signed; a tree rebuilt with no checkpoint the repository itself verified says the history has not been checked (`provisional`, *seen* on the real run); a declared base that differs from the real parent is compared with the real parent and says so; no signature outcome is shown; the view is read-only: nothing is signed, selected, landed or merged (INV-2) |
| **Logs and counters** | file names or contents leaking into logs | *test*: the built binary under the real sandbox, a canary name and a canary content, the whole log holds neither; *seen*: the server log of the end-to-end run has 0 lines with the file names; counters carry no name or content |
| **Accessibility and plain words** (RFC 012) | a reviewer who cannot read or operate the view | structural rules (17) over every state of the view in both languages; the diff colours are supplementary (a "+"/"−" marker and hidden words, borders in forced colours); contrast tested in both themes; no sideways scroll at 320 px and no target under 24 px, measured once in Chromium (200 runs); a Tab walk with a visible focus on 822 of 822 elements; **no assistive technology and no other browser tried** (`docs/accessibility.md` says so) |
| **The gate tools** (`cargo-deny` 0.20.2, `cargo-audit` 0.23.0) | a gate's verdict changed by a tool update | pinned in all three workflows, one version across them, `--locked`, enforced by `pin-check` (8 new tests); an older tool fails loudly on a newer advisory format (*measured*: `cargo-audit` 0.20.1–0.21.2 exit 1 on CVSS 4.0, older ones do not build) |
| **`planeter-client propose --proposal`** (IS-59) | a documented action that cannot work | found by running the real client against the real server; fixed in the client only (no `target_ref` with a proposal id; `--title`/`--description-file` with `--proposal` refused locally); *test* with two revisions through the real client and a mutation (`target_ref` back → the server's refusal); the server stays strict |

## What was not done (said plainly)
* The 0.6.0 and 0.5.0 lists still hold: **no external penetration test and no fuzzing campaign**; the sandbox is not exercised inside the image in CI; no second factor (RR-10); in-memory rate limits (RR-11, RR-13).
* **No person using assistive technology has tried the new pages**, nor Firefox or Safari; forced colours were not checked on a real system.
* **The view needs the spool** (`PLANETER_SPOOL_DIR`): without it the server has no proposals at all (documented).
* **The upgrade rehearsal of 0.6.0 covers small databases**; 0.7.0 changes no table and no format.
* **A failed request's reason is shown only with `--verbose`** in the client (the server's hint points to it): a small usability gap, not a security one.
* **The Japanese of the new messages is the owner's reading only** (95 messages read and accepted on 2026-11-17, then 24 of them reworded after the architect's second reading and read again and passed the same day; the sign-off record is data and `planeter-i18n-sheet --status` lists 0 newer messages). No second reviewer, no user of Japanese assistive technology.

## Findings made on the way, all closed before this review
The engine put an English marker inside data (and the page matched it by text, which a hostile line could imitate) → `cut_chars`/`path_cut_bytes`; an unbounded wait per revision → eight waiters; an old cache pointer would have kept serving old markers → versioned key and a miss rule; `planeter-client propose --proposal` could never work (IS-59, since 0.5.0); the dry run of the publish step at an already released version number cannot pass (documented); Japanese pages scrolled sideways at 320 px (fixed and measured).

## Recorded for later
**IS-60.** The release builder's BuildKit pin (v0.33.1) has two published advisories that name it (a Git source resolved twice crashes the daemon; an untrusted client of the control API). Neither is reachable: the builder is an ephemeral runner, the only client is our workflow, the definition is our Dockerfile with no Git source. Move to ≥ v0.34.2 at the next release-chain change, with a rehearsal.
