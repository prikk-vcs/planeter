# RFC 013 — Maintainer keys after creation: adding, rotating by addition, and what cannot be done yet

**Status.** **Accepted 2026-11-22** (the owner: "Accepted", after reviewing the three open points against the philosophy, SCHEDULE D-110; drafted 2026-11-21, the owner having confirmed the order, RFC 013 first and RFC 014 second, D-106). **D-1, D-2, D-4, D-5 and D-6 may be built; D-3 is accepted as a design but has a decision gate and is not to be built** until the architect has read prikk's 0.59.0 design for trust records and the owner has decided (below). Handoffs: `handoffs/013-maintainer-keys/` (`keys-foundation-handoff-v1.md` first).
**Tracks.** ROADMAP "After 0.8.0"; threat model `RR-20`, `INV-2`, new `T-21`; RFC 008 (delivery, D-2 and D-3), RFC 004 (creation adopts exactly the typed keys), SCHEDULE D-105, D-106, D-107.
**Touches.** `planeter-prikk` (two readers: the trust list, one file read), `planeter-store` (a small table of key events), `planeter-transport` (the delivery engine: one more report line, one more refusal, one step in the install), `planeter-web` (the repository page, the review view's warning), `planeter-client` (`deliver`: one more question), `planeter` (the first operator subcommand, `planeter operator key add`), the creation form (how many of the 64 key slots are left), docs. **Not here:** removing or revoking a key (prikk cannot do it without breaking `verify`: PK-90, PK-91); linking a key to an account (RFC 014); a key held by the forge (never, INV-2); required approvals.
**Evidence.** Ledger **PK-92 (measured: the cost of many trusted keys)**, PK-33, PK-34, PK-60 (a key an archive merely carries changes nothing), **PK-90 and PK-91 (measured: removing any key that signed anything makes `verify` fail; prikk's design round is 0.59.0, a build 0.60.0 at the earliest; with every key lost prikk does not freeze the repository: an operator adopts a new key with `trust maintainer add`, no signature asked for)**.

## Summary

A repository's trusted maintainer keys are the creator's, fixed at creation (RFC 004). Two things follow that a long-lived forge cannot accept. **A lost key** leaves a repository unable to take work from anyone whose key is not on the list: nobody can be added. **A stolen key** can deliver anything it signs, and nothing can withdraw it (RR-20). This RFC fixes the first and states the second plainly. It adds keys, by **two paths that never need the forge to hold a key or to remove one**: (1) the **operator's act** for when no key can sign, visible to everyone on the repository page; (2) **a maintainer's own delivery**, signed by a key the repository already trusts, which says in its report, before it is confirmed, that it makes the repository trust more keys. Rotation is addition: the new key signs new work, the old key stays trusted. **Revocation is not designed here**, because prikk 0.58.0 has no way to retire a key from a point (PK-90, PK-91); the RFC says what a maintainer can and cannot do today and waits for prikk's design.

## Why now, and why not simply a button

The forge's safety argument (RFC 008 D-2) is that a delivery is checked in a stage that trusts **exactly the live repository's adopted keys**, never the archive's. Keys are therefore the root of everything a delivery can do. Changing them is the most sensitive act on a repository, so it must be (a) never possible for a stolen **token** alone (C-20c: a token is one factor, a key is the other), (b) visible to every reader afterwards, (c) impossible to do silently by a proposal, and (d) not invented by the forge: **the forge signs nothing**, so the only signed statement it can read is what prikk itself seals into history.

## Decisions

- **D-1 — The forge never calls `trust maintainer remove`, and never makes a key "retired" in any display.** prikk's `remove` means "this key's signatures never count" and fails `verify` for everything the key sealed. A word like "retired" or "revoked" on a page would claim something no component enforces. The pages say "added" and show where a key came from, nothing else. When prikk's design round (0.59.0) and a later build (0.60.0 at the earliest) give a real retirement, a new RFC uses it. *Test: a source scan holds that no planeter code spawns `trust maintainer remove`; a page test holds that no page says retired or revoked.*
- **D-2 — The operator's act (for when no key can sign, and the first thing built).** The person who runs the server (the **operator**, trusted, ASSUME-1) adds a key to one repository with a new subcommand, the first of **`planeter operator`**: `planeter operator key add OWNER/NAME --key-id ID --public-key HEX --reason TEXT`. **The server must be stopped.** The repository lease is in-process and a second process against one store is refused at start (RFC 004 D-7, `process_lock`), so a command that ran beside a live server would race it; instead the command **takes the same process lock itself** and, if a server holds it, stops with one sentence ("The server is running. Stop it, run this again, then start it.") and changes nothing. It is a rare act (every key lost), so a short stop is the honest price, and no door into a running server is opened (no socket, no new route). It validates the key (64 lowercase hex characters; the id is the one prikk derives from it), refuses a key already trusted, **refuses a repository that is flagged `needs_recovery` or has an unfinished delivery or intent** ("Start the server and let recovery finish first"), writes an **intent**, calls `prikk trust maintainer add`, runs `verify`, bumps the revision counter, records a **key event** (D-4) with the reason, and removes the intent; a kill inside it is finished or abandoned by the next start's recovery like any write (the add is idempotent). It never touches history, a proposal or the key's holder. **Why `operator`, not `admin`:** the pages and documents already use "administrator" for a repository's administrator role (a person signed in on the web); this command is for whoever has a shell on the server and its data, and its name says so. `--help` says: "For the person who runs this server. It needs the server's data and cannot be run from the web." *Tests with real prikk: the add; the refusal of a malformed key, of a trusted key, of a running server (a real server process holding the lock), of a flagged repository; the repository `verify`s clean; a kill at every step; the key is usable for a delivery afterwards; a delivery before it is refused `unadopted_key` as today.* **The honesty rule:** this act is the one place where one person can change who may deliver, so it is **never silent**: the repository page says "Added by this server's operator on {date}: {reason}" next to the key (D-4), and the command prints the same sentence.
- **D-3 — A maintainer's own delivery adds keys (decision gate).** *Proposed design, if prikk offers nothing better:* a **reserved file in the project's branch**, `.planeter/maintainer-keys`, lists keys the maintainers want trusted, one per line (`key-id public-key-hex`, `#` comments). It is ordinary content that a maintainer commits and seals with their own prikk and key, so the statement is **signed by prikk's own machinery, in history, reviewable**. After a delivery's install (and only then) the forge reads the file at the new tip (one bounded `cat`, sandboxed), and **adds the keys not yet trusted** with `trust maintainer add` (never removes: a line deleted from the file does nothing, and the page says so). Consequences that are part of the design, not left to chance:
  1. **Two deliveries, never one.** The stage trusts the live set (RFC 008 D-2), so a delivery that carries the file's change *and* blocks sealed by the new key is refused `unadopted_key` with the sentence "Deliver the change that adds the key first; deliver the key's work after." The first delivery adds the key; the second carries its work.
  2. **The report says it, before the maintainer confirms:** "This delivery makes this repository trust {n} more key(s): {fingerprint, eight groups}. Check that these are the keys you mean." The client asks a **separate** question for them, and `--yes` alone does **not** answer it (`--trust-new-keys` does, and is documented as the way a script says it knows).
  3. **A malformed file refuses the whole delivery** (`keys_file_invalid`, with the line number); nothing is half-applied. Two bounds, both said in words: **at most 8 new keys in one delivery** (a human has to compare each fingerprint; this is a readability bound, not a safety one) and the **total bound of D-6**.
  4. **The review view warns.** A proposal whose revision changes that path is marked "This change would make the repository trust a new key once a maintainer delivers it" on the changes page and in the JSON (`changes[].effect: "adds_trusted_key"`), because a maintainer could seal a contributor's patch without reading every file (the confused deputy, T-21).
  *Decision gate:* **before any build of D-3** the architect reads prikk's 0.59.0 design for trust records and the owner decides between this convention and prikk's own mechanism if it exists. A convention in users' repositories is a long commitment; building it ahead of prikk's answer is a choice for the owner, not for the schedule. D-1, D-2, D-4 and D-5 do not depend on it.
- **D-4 — Every key has a provenance, shown to everyone who can see the repository.** A table `repo_key_events` (repository, key id, public-key fingerprint, source `creation | delivery | operator`, the delivery id or the operator's reason, date). The repository page's existing "Keys this repository trusts" list (under `<details>`) shows per key: "From the repository's creation", "Added by a delivery on {date}", or "Added by this server's operator on {date}: {reason}". The JSON `refs` gains `trusted_keys[]` with the same. The reason text is display-safe (the project's cut rules), at most 200 characters. *Tests: the three sources on a real repository; the page in both languages; no page claims more than the table.*
  **A key that has no recorded source is shown as such:** "Source not recorded". The truth about *which keys are trusted* is prikk's list; the table says only *how* each came. A key prikk lists and the table lacks (added outside planeter, with prikk directly, by someone with a shell) is shown without a claim. When 0.9.0 first starts, the keys every existing repository trusts are recorded once as "From the repository's creation (recorded when 0.9.0 started, {date})": in 0.8.0 the creation form was the only way a key got there, and the sentence says when the record was written.
- **D-5 — What a maintainer can and cannot do today, said on the page and in `docs/keys.md`.** *Can:* add a new key (D-2, D-3), rotate to it (it signs new work; the old key stays trusted), keep several keys. *Cannot:* remove a key; mark a key retired; make history signed by a key stop counting. **A lost key:** keep it trusted (removing it would fail `verify`), add a new one. **Every key lost:** the operator's act (D-2) is the way out (prikk does not freeze the repository, PK-91). **A stolen key:** there is no remedy that keeps the repository's history verifiable; the honest advice is to **stop delivering with the other keys, tell everyone who relies on the repository, and wait for prikk's design**; a successor repository cannot omit the key either (history it signed would fail `verify` there too). This is the largest residual risk of the project and is not hidden (RR-20 stays).

- **D-6 — One bound on the number of trusted keys: 64, the number creation already has.** Creation keeps an archive's findings only if it carries at most `KEYS_MAX` = 64 keys (`planeter-prikk::findings`), and prikk's output cap for `trust maintainer list` was measured for 64 keys (6.9 KB). **That one number is the bound for every path** (creation, a delivery, the operator), so a person never meets two rules. It is derived from measurement, not guessed (ledger PK-92, prikk 0.58.0): trusted keys 17 / 65 / 257 / 1,025 → `verify` 7 / 10 / 29 / 553 ms; the trust list 2.2 / 8.2 / 32 / 129 KB; an archive of the repository 10 KB / 70 KB / 0.9 MB / **13.8 MB** (every key added leaves a stale trust record the size of the whole list, so the archive grows with the square of the number of adds until `prikk compact --trust-policy` reclaims it: 13.8 MB → 140 KB). At 64 keys nothing is noticeable and no compaction is needed; far beyond it the cost leaves the linear. **A smaller total (the draft said 16) was wrong:** creation already allows 64, a repository made with 40 keys would have been over the limit on its first addition, and because keys cannot be removed (D-1) every rotation uses a slot for good, so a low bound is a cliff with no way down. **What the person is told at the bound** ("This repository already trusts the most keys planeter supports: 64. Keys cannot be removed yet, so no more can be added.") and what is true: until prikk can retire a key (PK-91), the only way on is a new repository with new history. A repository created with 64 keys has no room to rotate: the creation form says how many slots are left ("{n} of 64 keys; each key you add leaves one less for the repository's whole life"). If the bound is ever raised, `compact --trust-policy` after every add becomes part of the same change (a measured one).

## What does not change

The delivery rule (RFC 008 D-3) and its stage; the owner-accepted sentences; the token factor (C-20c): a delivery still needs a maintainer's full-scope token **and** a signature by an adopted key, and a delivery that adds a key needs both **and** the maintainer's second confirmation. The forge signs nothing; ENF-2 holds.

## Threats (draft of T-21)

- **A stolen token alone adds a key.** Not possible by D-3: the token can deliver only history an adopted key signed. By D-2 only the operator, on the host. *Mitigation tested: a `full` token with no adopted-key signature gets `unadopted_key`.*
- **A contributor's proposal smuggles a key (confused deputy).** A maintainer seals a patch that touches the keys file among many files and delivers. Defences, in order: the review view's warning (D-3.4), the report line and the separate question (D-3.2), the two-delivery rule, the visible provenance (D-4). Residual: a maintainer who confirms a fingerprint list without reading it. **Accepted, written in RR-21.**
- **The operator abuses D-2.** The operator already controls the host (ASSUME-1); the act is never silent (the page shows it, the reason is public) and is recorded. Residual: an operator can still read the database; not made worse.
- **A malformed or hostile keys file** (huge, binary, a key id that does not match its key, a duplicate). Bounded (size, 8 new keys per delivery, the total bound of D-6), validated, refused as a whole; the key id is recomputed, never trusted.
- **Racing deliveries or an add during a delivery.** One write lease per repository; the add is part of the install's lease (D-3) or its own lease (D-2); a delivery whose stage was built before the add re-checks the rule under the lease as today.
- **A key added that signs nothing useful or collides.** Harmless; the total bound of D-6 and the visible list bound it.

## Phasing

- **0.9.0 (proposed):** D-1 (scan and page test), D-4 (table and display) and D-2 (the operator's act, `planeter operator`) and D-6, `docs/keys.md`. Nothing here changes a user's repository, and nothing waits for prikk.
- **After the gate:** D-3, only as decided by the owner after prikk's design is read. If prikk offers a native signed trust record, a short RFC supersedes D-3 and this file keeps D-1, D-2, D-4 and D-5.

## Open questions

1. **(Owner, gate for D-3)** The file convention now, or wait for prikk's own mechanism? *Architect's recommendation: build D-1, D-2 and D-4 for 0.9.0 and wait for prikk's design for D-3: a convention inside users' repositories is the part that is hardest to take back, and the waiting costs only self-service (the operator's act covers the need).*
2. **~~The cap of 16 keys.~~ Settled in D-6 (64, the number creation already has, measured).** What stays open is only whether the owner wants the bound raised later, which is a measured change that brings `compact --trust-policy` with it.
3. **~~`planeter admin` as a family.~~ Settled in D-2: the family is `planeter operator`** (for whoever has a shell on the server; RFC 014 adds to it). Its shape (one binary, a subcommand tree, a `--help`, translated messages, no secrets on the command line, **the server stopped**) is decided here only for `key add`; RFC 014 decides whether account commands may run beside a running server (they touch the database, not a repository).
4. **A key's name.** prikk's key ids are derived; a human label ("Aki's laptop") would help a reviewer of the list but is a new thing to keep true. Not in this RFC.

## Tests and evidence the handoffs will ask for

Real prikk: add by the operator on a repository that has one key, then a delivery signed by the new key accepted; the same delivery before the add refused; a key lost (its seed deleted) and the operator's add; kills at every step of D-2; a source scan for `remove`; the page and JSON in both languages with the three provenances; the structural accessibility rules over the key list; mutations (the add skipping `verify`; the event not written; a page saying "retired"). For D-3 (after the gate): the two-delivery refusal, the separate question and `--yes`, the malformed file, the review-view marker, the confused-deputy scenario end to end.
