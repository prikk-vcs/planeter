# RFC 014 — `planeter operator account …`: the operator's commands, run beside a live server — Implementation Handoff (v1)

| | |
|---|---|
| Document | Second handoff of RFC 014 step 1. It adds the **account half** of the `planeter operator` family (the token half is the next handoff): `account create`, `set-password`, `disable`, `enable`, `link-oidc`, `unlink-oidc`, `grant`, `revoke`, `list` (with `--check`) and `show`. ## The commands

```
planeter operator account create HANDLE --name TEXT [--password-prompt | --password-fd N]
planeter operator account set-password HANDLE [--password-fd N]
planeter operator account disable HANDLE --reason TEXT
planeter operator account enable HANDLE
planeter operator account link-oidc HANDLE --issuer URL --subject TEXT
planeter operator account unlink-oidc HANDLE --issuer URL --subject TEXT
planeter operator account grant OWNER/NAME HANDLE --role read|write|maintain|admin
planeter operator account revoke OWNER/NAME HANDLE
planeter operator account list [--check]
planeter operator account show HANDLE
```
All take `[--lang en|ja]`; `planeter operator --help` and `planeter operator account --help` describe them (the existing help text for `key add` is kept as it is).

## Change scope

**T1 — The shared frame.** Extend `operator.rs`'s parser and exit codes to the new words without changing `key add` (its tests pass untouched). The account commands **do not take the process lock**; they open the database the way `key add` does (the database must exist; it is never created), and a database that stays locked past the busy timeout gives one sentence and exit 5 with nothing changed. **Exit codes as for `key add`**: 0 done, 1 refused (nothing changed), 2 the command line, 5 local files or the database; 3 is not used here; 4 only if a change was made and its event or a second step failed (it cannot with one transaction: say so in `--help`). Messages are the server's own catalog (`operator.account.*`), English and Japanese, one sentence each with what to do, in RFC 012's plain words and the glossary (no 保持, no 預かる); they ship **flagged** until the owner reads them: give `--status` and extend the reading file. Never read `PLANETER_OIDC_CLIENT_SECRET` or any other secret of the server (the canary test of `key add` is repeated).

**T2 — Passwords without a command line.** `create --password-prompt` and `set-password` **read the password from the terminal without echo, twice**; `--password-fd N` reads it (one line, then the same line again is not needed) from an open file descriptor for scripts. **No argument, no environment variable, no file name carries a password; a password that appears in `ps`, the environment, a log, an event, an error or the database in any form but the Argon2id hash is a defect** (a canary test over all of them, including a failing check of the rule: the error names the rule and never the password). **No new dependency and no `unsafe`**: the lock holds only `libc` (and the project forbids `unsafe` in these crates: check the lint), so the prompt turns echo off by running `stty -echo` on the terminal with a **guard that restores it on every exit path** (normal return, error, panic unwinding); a SIGKILL cannot be guarded, and the help says "if your terminal stops echoing, run `stty sane`". If standard input is not a terminal and `--password-fd` is absent, the command **refuses** (exit 2) and says so. The password goes through `check_new_password` (the rule of D-4: the error says which rule and what to do) and then `AccountService`. Without `--password-prompt`/`--password-fd`, `create` makes an account **with no password** (it signs in only through a linked identity); `set-password` on an account whose password sign-in the operator has switched off is allowed (the hash is kept for if it is switched back on).

**T3 — Each command, exactly.** Each is one `AccountService` call (one transaction, its event inside it) plus the reads it needs, a refusal changes nothing, and each success prints **the same sentence the account's holder will read in their log** (the event's wording) and, where useful, one line of what it means:
- `create`: handle rule and uniqueness errors say which rule; the result says the account has or has no password; the display name is shown back.
- `set-password`: ends all the account's sessions (say so in the result); it does not touch tokens.
- `disable`: **before it acts, prints the repositories for which this account is the only administrator** ("These repositories will have no administrator until you grant one: …": a bounded list, at most 20 names then "and N more"), then disables, ending sessions in the same transaction; the reason is 1 to 200 characters, one line, as `key add`'s. `enable`: restores; says that tokens work again until their expiry and that ended sessions do not return.
- `link-oidc`/`unlink-oidc`: **the issuer must be the configured one** (`PLANETER_OIDC_ISSUER`; if none is configured, refuse with a sentence that says so); an identity already linked to another account is refused and never moved; the subject is never shown in a result or an event (the event names the issuer's host only, as the foundation does).
- `grant`/`revoke`: the repository must exist, the account must exist and not be disabled (granting to a disabled account is refused with a sentence); **the result names the account's display name** so a mistyped handle is seen at once; **each role is described in one plain sentence** in `--help` and in the result (read: look at it and clone it; write: also propose work; maintain: also ask for a delivery and review proposals; admin: also manage who has access); `revoke` refuses to remove the **last administrator** of a repository unless `--allow-no-admin` is given (a plain sentence says what that leaves); events for the person affected (`role_granted`, `role_revoked`, with the repository name display-safe).
- `list`: handle, display name, state (active/disabled), has-password yes/no, linked-identity yes/no, created; sorted by handle; **`--check`** reports instead the accounts with `handle_collides = 1` grouped by key ("these differ only by case; they keep working and were not renamed"), and exits 0 whether or not there are any (it is a report); bounded output (at most 500 lines, then "and N more", with the count).
- `show`: the same fields for one account, its repositories' roles (bounded), its **last 50 events** (the foundation's `recent`), **never a hash, a token or a subject**.

**T4 — Beside a live server (the point of this handoff).** The tests start the **real built server** (real prikk and sandbox where the repository part needs it) and run the commands **while it serves**: (a) `create` then the person **signs in at once** (password, and through a stand-in provider for `link-oidc` as the existing OIDC tests do); (b) `disable` ends a live session and refuses a live token **on the very next request** (the foundation's guarantee, now through the command); `enable` restores the token; (c) `set-password` ends sessions, the old password stops and the new one works; (d) `grant` lets the person act on the repository at once, `revoke` stops them; (e) two commands at once and a command while a request writes (no corruption, no deadlock; a held write lock gives the timeout sentence, exit 5, nothing changed: hold the lock from the test with a second connection); (f) `key add` still refuses beside a running server (exit 3) as before. Also a database with a case collision (the foundation's fixture): `list --check` reports it and every other command works; a real 0.9.0 data directory (the foundation's migration fixture): all commands work on it.

**T5 — Tests and mutations.** For each command: the happy path, every refusal compared against a dump of every table before and after (equal), the same refusal in English and Japanese by `--lang`/`LC_ALL`, and the exit codes. The canaries of T2. **Mutations, each shown failing once and reverted:** a command that takes the process lock (it would refuse beside a server: T4(f)-like test for accounts); the event not written; `disable` without ending sessions; `grant` to a disabled account allowed; `revoke` removing the last administrator; `link-oidc` accepting another issuer; the password echoed into the result; the `stty` guard not restoring on error (a test with a fake `stty` in `PATH` that records its calls: echo off, echo on, in that order, on success, on a refused password, and when the second entry does not match).

## Non-change scope
No token command (the next handoff), no page, no route, no API, no OpenAPI change, no provisioning, no change to `authorize()`, the foundation's services or schema (a fix there is reported, not made silently), no issuer allowance (its own handoff), no new dependency, no `unsafe`, no change to `key add`. No sign-off record, baseline, `ja.signed` or `SignOff`. No tag, release or upload.

## Acceptance criteria
Every command works beside a running server (T4), changes nothing when it refuses, never shows a secret, and writes the event the holder will read; `key add` unchanged; the canaries clean; all gates green with tests with prikk 0.58.0 three times in a row; CI green on all eight jobs; `tools/repeat-under-load.sh 20` on the new test file(s) clean.

## Required evidence and review-request format
Commits (hash → what, by task, each compiling and passing the tests it touches); transcripts of a real run of every command in English and in Japanese (with the server running and visible in the log: counts only); the `--help` texts; the table of refusals with the before/after dump equality; T4's results; the `stty` guard test; the canary results; the mutations (failing output, then clean); `planeter-i18n-sheet --status` and the reading-order file for the owner (the new messages in the order of use: create, set-password, disable/enable, link, grant/revoke, list/show, the errors); the gates in a clean worktree (fmt, floor, pin, clippy, tests with prikk 0.58.0 three times in a row and without, `cargo deny`, `cargo audit` on a fresh database, ENF-2, doc, msrv) with commands, exit codes, tool versions, the advisory-database HEAD and count; deviations and open questions (say plainly what you could not show).
