# RFC 014 — Four things the documentation exposed, and the one control the RFC promised and nobody built — Fix Handoff (v1)

| | |
|---|---|
| Document | `accounts-docs-review-request.md` (`99fb149`) is approved: the page is plain and honest, every sentence it quotes is held by the catalog, the ledger and the code, and my targeted run of its tests (`accounts_doc`, `keys_doc`, `language_rules`, `plain_words`: 25 tests) passed on that commit with CI green. Quoting every sentence found six things; four are fixed here, two are decided as "leave". And it found a **gap against the accepted RFC**: **D-5, `PLANETER_LOCAL_PASSWORDS=off`, was never built** (nothing reads it), and it is the one control that lets an operator who uses a provider have the provider's second factor **and nothing weaker beside it**: with a provider configured, a person with a local password can still sign in by it, with no second factor (RR-10). It was written into the RFC as a step-1 setting (D-5, D-13's neighbour); the handoffs missed it. |

## Change scope

**T1 — `PLANETER_LOCAL_PASSWORDS` (RFC 014 D-5).** Read at start like the other provider settings (`provider_env.rs`): `on` (the **default**) or `off`; anything else refuses the start with a sentence (English and Japanese, flagged); `off` **without a provider configured refuses the start** with a sentence (it would leave nobody able to sign in). With `off`: the sign-in page shows **only the provider's button** (no handle or password fields) and says why in one sentence; `POST /login` (the password form) is answered **exactly as a wrong password is** for every account (the same status, the same page, **the same single dummy verification**: no oracle that says whether password sign-in is off for a given account, IS-31); **no password hash is touched or deleted** (switching back to `on` restores them); `planeter operator account create --password-prompt` and `set-password` **still work** and say, in one sentence, that password sign-in is **off on this server** (read from the environment the command already reads: add `PLANETER_LOCAL_PASSWORDS` to the short list of variables the account commands read, and to `docs/accounts.md`'s list); tokens and sessions are unaffected. The start-up line says it is off (one line, English and Japanese). **Tests (real router):** off + provider: the page has no password field and shows the provider's link; a correct password and a wrong one for an existing account **and** for an unknown account all answer the same and cost one verification each; provider sign-in still works (the in-process flow of the existing tests); `on` is exactly today's behaviour (the existing sign-in tests pass untouched); the start refusals; a mutation: `POST /login` still accepting a correct password when off → caught. **Document it** in `docs/accounts.md` (a short subsection, with its risk: with it off and the provider down nobody can sign in through the web; the operator's commands and a restart with `on` are the way back; recommended with a provider), held by `accounts_doc.rs` (the setting must be read in the source and on the page: the test already checks this).

**T2 — Token commands get their own exit-code text.** `planeter operator token --help` prints `operator.account.help.exit_codes`, which says "2 … or no terminal for a password": a token command has no password. Add `operator.token.help.exit_codes` (English and Japanese, flagged) without that clause and use it in the token help; `docs/accounts.md` and its test follow.

**T3 — `operator.account.done.disabled` says less and says it true.** "…and others can still read its repositories" promises more than is true (a private repository of the disabled account is not readable by others). Replace it with the true, shorter statement that **nothing of the account is deleted** (its repositories, proposals and comments stay, as before); English and Japanese, flagged; the page and the test follow.

**T4 — The reading file's group 3.** The three sentences nothing writes yet (`account.event.session_ended`, `password_changed`, `signed_in_new_method`) go to a **sixth, optional group at the end ("sentences for pages that do not exist yet: read them with step 2")**, so that the owner reads the log as it can actually be written (28 messages) and may skip those three (3) without leaving the first five groups incomplete; counts must still sum to the tool's total (now larger by the new messages of T1–T3: give the number).

**T5 — `tools/gates.sh`: a relative `--sheet` path** is made absolute **before** the script changes directory (the dev team lost a run to it): one line and a test (a relative path now works; an absolute one still does).

## Decided "leave" (do nothing)
* The repeated sentence of `token create` (the event's sentence, then "A token for … was created. Its id is …"): it states the id once and costs nothing: **leave**.
* The Japanese name of the operator in two wordings (このサーバーを運用している人 / このサーバーの運用者): **both already exist in text the owner signed off** (`operator.help.purpose` and `operator.done`), so it is the owner's to settle at the reading; **leave** both, and keep it on the reading list of words to look at.
* "single sign-on" on `page.sso_unlinked.body` against "sign-in provider" everywhere else: that page's text is signed off; recorded as a wording item (STATUS), **not changed now**.

## Non-change scope
No other message or setting, no schema, no new page, no change to the foundation's services or to the provider code, no sign-off record, baseline, `ja.signed` or `SignOff`, no new dependency or `unsafe`, no tag, release or upload. `docs/RELEASING.md`, the ledger, SCHEDULE, STATUS and the threat model are the architect's.

## Acceptance criteria
`PLANETER_LOCAL_PASSWORDS=off` works as above with the tests and the mutation; the three wording changes are made and held by the document test; the reading file's counts equal `--status`; the gates script accepts a relative sheet; `tools/gates.sh --tier review` green on the commit (and CI green on all eight jobs).
