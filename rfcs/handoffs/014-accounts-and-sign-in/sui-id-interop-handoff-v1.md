## Change scope (a test procedure, its evidence, and a report: no product code)

**T1 — Build and run the provider.** In a **throw-away work directory under `.git-exclude/tmp/`**: a worktree of the sui-id tag you chose (say which and why: the newest tag after reading its CHANGELOG, unless the CHANGELOG says otherwise); `cargo build --release` of its binary with the Rust version its manifest requires (its `rust-version` is 1.95; use the toolchain you have that satisfies it and say which) **under `tools/run-capped.sh`** with a target directory of its own that you delete at the end; `sui-id init`, its setup (the one-time setup token it prints), an administrator, **one ordinary test user**, and **one OIDC client** for planeter (a public client with PKCE, and a second confidential client with a secret: the two forms planeter speaks), with the redirect URI planeter would use. sui-id's issuer must be https: put a **TLS terminator with a throw-away CA** in front (as the 0.8.0 end-to-end look did) and keep the CA in the work directory. Record the exact commands and the sui-id version printed by its binary.
**T2 — Drive planeter's provider code against it, in process.** In `crates/planeter-auth/tests/` a test file `interop_sui_id.rs`, **`#[ignore]` by default** (it needs an external binary: it must not run in the normal gates or in CI), run on demand with `PLANETER_SUI_ID_URL` (the issuer of the running test provider) and `PLANETER_SUI_ID_CA` (the throw-away CA file) and the client settings in environment variables; it uses the same method as `oidc_private_provider.rs` (the real `OidcProvider`, the real `curl` through a wrapper that trusts the CA, the egress guard with the one-host allowance for the issuer's authority). It **must not run in CI** and must say plainly, when skipped, why. A test user's browser step is done by the test with plain HTTP calls to sui-id's own login form (a cookie jar, the form fields it documents): say which endpoints it used.
**The checks (each one a named test, each with its outcome recorded as measured; a failed check is a finding, not a failure of the handoff):**
1. **Discovery** parses, `issuer` equals the configured issuer exactly, the endpoints are on the issuer's authority (so the one-host rule holds), and the algorithms the document lists (ID-2: EdDSA only).
2. **The authorization-code flow with PKCE S256** completes for the **public** client and for the **confidential** client (`client_secret_basic`: ID-8/the sui-id reply listed `basic`, `post` and `none`): the ID token verifies against the JWKS with **EdDSA**; `iss`, `aud`, `exp`, **the nonce** are checked.
3. **The claims** of the ID token: the exact set (ID-2: `iss`, `sub`, `aud`, `iat`, `exp`, `nonce`, `jti`, `acr`, `amr`, and `email`/`email_verified` under the `email` scope); `sub` is 36 characters in the hyphenated lowercase UUID form (ID-6) and is the **same on a second sign-in** by the same user; `email_verified` is **false** (ID-1) and planeter stores no email from it (the account row is unchanged); **no `name`, no `preferred_username`** in the ID token (ID-2) and **no userinfo request is made** by planeter (count the provider's requests).
4. **A replayed code** is refused by the provider and by planeter (the second exchange fails); an **expired code** (if the provider's lifetime can be waited out or lowered, say how) and a **wrong `code_verifier`** and a **wrong `state`** and a **wrong `nonce`** are refused.
5. **`prompt=login` is not read as a recent sign-in (ID-4).** With a live provider session for the test user, send the authorization request **with `prompt=login` and `max_age=0`** (planeter itself sends neither: do it with a hand-made URL) and show whether the provider **asks for a new sign-in or returns a code at once**; either way record what the ID token carries (an `auth_time`? no) and **that planeter's claim ("a sign-in to planeter within 15 minutes") is unchanged by it**.
6. **Key rotation (ID-7).** Rotate the signing key at the provider in the way its documents describe (say how): check the `Cache-Control` header of the JWKS (**`public, max-age=300`** as told), that the previous key stays in the set, and **the sign-in in the minutes around the rotation**: a sign-in whose ID token is signed by the **new** key while planeter's JWKS cache holds the **old** set must succeed through the **one `no-cache` refresh** (a caching stand-in in front of the provider that serves the stale set to requests without `no-cache`, as `jwks_refresh.rs` does, but now in front of the real provider); show it with the refresh and, by disabling the header in the wrapper, without.
7. **The provider slow, down or answering garbage** (stop it mid-flow; delay its token endpoint beyond planeter's 15-second bound; a hand-made discovery document that is not JSON): each ends with planeter **refusing the sign-in and saying so** (the `OidcError`), never signing anyone in, and **never a hang**.
8. **Offboarding (ID-5, the sui-id architect's second added item).** Sign the test user in through the provider into a planeter session (the in-process authenticator and session store, as the real handlers use them), **disable the user at sui-id** (its admin way), and measure **what planeter does**: the planeter session stays valid until its lifetime (`PLANETER_SESSION_HOURS`); a **new** sign-in through the provider fails at the provider. Also show the provider's own statement that a disabled user's **refresh tokens, sessions and pending codes are revoked in the same transaction** if you can show it by using the refresh token before and after (planeter does not use refresh tokens: this is a measurement of the provider's claim, labelled as such). **State plainly in the report that planeter has no refresh check** (RFC 014 open question 7, the owner's).
9. **Cost and size**: the size of the discovery document, the JWKS and the ID token; the number of requests planeter makes per sign-in (expected: discovery, token, JWKS: three); the time of a sign-in against the local provider.
**T3 — The findings and the ledger.** A report with one row per check: **expected (the ledger row it tests) → measured → confirmed / corrected / not shown**, with the evidence file for each. **Do not edit `docs/src/planeter-idp-ledger.md` or `docs/accounts.md`** (the architect folds the result into the ledger, as ID-11 onward, and decides what the document may say). Do not write "tested with sui-id" anywhere yet: the report may *propose* the sentence, with the version and the date and exactly the checks it would cover.
**T4 — The letter.** Draft `…/upstream/sui-id/send/draft/<date>-what-we-measured-in-0.92.0.md` (use the real version): what was confirmed, what differs from what the sui-id architect told us (**each with the measurement**), anything that looks like a defect **in sui-id** described as a reproduction and **not** as a security claim, **and whether anything seems a security matter: if so, do not put the detail in the letter or the report; say only that you found something and write the detail in a private file under `.git-exclude/` for the architect** (sui-id's own policy is private reports).
**T5 — Leave nothing behind.** The run's work directory, the sui-id target (tens of GiB: say its size), the TLS material, the test user's data, and every process (the provider, the terminator, a caching stand-in) are removed or stopped **by explicit path or PID** at the end, **also when a check fails** (a trap, as `tools/gates.sh` does); `ps`, `df` and `git worktree list` before and after are in the report. The 15 GiB `gate-target-…` directory is not yours to remove.

## Non-change scope
No product code; no change to the sui-id repository (you build from your own worktree of a tag); no ledger or `docs/` edit; no "tested with sui-id" sentence anywhere; no new dependency of planeter (the test uses what `planeter-auth`'s tests already use; plain HTTP calls through `curl`); no network access other than to the local provider; no sign-off record, baseline, `ja.signed` or `SignOff`; no tag, release or upload.

## Acceptance criteria
Every check has a recorded outcome with evidence, including the ones that fail or cannot be shown (said plainly); the test file is `#[ignore]` and skips with a reason; nothing of it runs in the normal gates or CI; the report's table and the draft letter exist; the work directory, the build and the processes are gone and shown to be; the normal gates (`tools/gates.sh --tier review`) are green on the commit; CI green on all eight jobs.

## Required evidence
Commits (hash → what); the tag and version tested, the CHANGELOG entries read, the exact commands to reproduce; the table of checks; the evidence files; the draft letter; the before/after `ps`, `df`, `git worktree list`; the build's CPU-seconds and disk (from `run-capped`'s output); deviations and open questions (say plainly what you could not show).
