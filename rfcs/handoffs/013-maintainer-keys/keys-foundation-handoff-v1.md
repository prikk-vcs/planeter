## Change scope

**T1 — One bound (D-6).** One constant for the largest number of keys a repository may trust, **64**, defined once in `planeter-prikk` (a new small module or beside `findings`), with a doc comment that gives the reason (RFC 013 D-6, PK-92: measured cost; creation's own bound) and a pure function `room_for(trusted: usize, adding: usize) -> Result<(), KeysBound>` where `KeysBound` says how many are trusted, how many were to be added and the bound. **`findings::KEYS_MAX` becomes that constant** (grep shows one definition and no other `64` standing for it; the output-cap comment that says "the 64 keys of the creation form" keeps its meaning). Creation uses `room_for` for the carried keys (the behaviour does not change: more than 64 carried keys is still the same refusal, same words). Unit tests: 0/64/65 boundaries, `adding = 0`, overflow-safe arithmetic.

**T2 — The record of where each key came from (D-4's data).** A new table **`repo_key_events`** in the metadata database, created idempotently at start, with its store trait, SQLite form and in-memory form, written the way `delivery.rs` is. Columns: `repo_id`, `key_id`, `public_key` (64 lowercase hex), `source` (`creation | delivery | operator`), `detail` (text, at most 200 characters, display-safe by the project's cut rules; the operator's reason, empty otherwise), `delivery_id` (nullable), `recorded_at` (unix), **`backfilled`** (0/1). **One row per (repo, key): the first record wins** (`INSERT … ON CONFLICT DO NOTHING`; a key cannot become "added" twice). Functions: `record(event)`, `events(repo) -> Vec<Event>` ordered by `recorded_at` then `key_id`. Tests: the unique rule, the order, a long or hostile `detail` is cut (not rejected) by the existing rule, both stores agree (the project's usual twin tests).

**T3 — The reader that joins the truth to the record.** In `planeter-transport` (beside the delivery's key view) a function **`repo_keys(driver, store, repo) -> Vec<RepoKey>`**: the **set** of keys is prikk's `trust maintainer list` (the truth); each `RepoKey` carries `key_id`, `public_key`, `fingerprint` (the eight-group form the delivery already prints: reuse its function, do not write a second) and **`source: Source`** where `Source` is `Creation {backfilled}`, `Delivery {delivery_id}`, `Operator {reason}` or **`NotRecorded`** — a key prikk lists and the table lacks. A row in the table for a key prikk does not list is **ignored** (never shown, never an error). Reading takes a **read lease** and the existing sandboxed driver. Unit tests with the stand-in driver and the real prikk: the four sources; the order (creation first, then by `recorded_at`); a table row without a key; a repository with no events (all `NotRecorded`); 64 keys.

**T4 — Creation records its keys.** When creation adopts the typed keys (the step that calls `trust maintainer add` for each), it records one event per adopted key, source `creation`, `backfilled = 0`, **at the end of creation's success path** (after the final `verify`). If the write fails the repository stays created and the failure is logged (no key named) and counted; the backfill (T5) covers it. Tests: a created repository has exactly its adopted keys recorded, none for a key left out; a failing store does not fail creation (the stand-in store fails once).

**T5 — The one-time background backfill of existing repositories.** After the server listens (the same place and manner as the unattended recovery thread: **on a thread of its own, so that the server is listening meanwhile**), a pass over every repository that has **no event rows at all**: read its trust list (read lease, one repository at a time, bounded by the heavy pool's admission like any prikk work), and record each listed key as source `creation` with **`backfilled = 1`**, `recorded_at` = now. Idempotent (a second start does nothing: every repository then has rows; a repository that gains a key later keeps its partial rows and is **not** touched again: only a repository with **no** rows is filled). A repository that cannot be read (hidden problem, needs recovery) is skipped and retried at the next start; the pass never changes a repository. At the end it logs **one line with counts only** ("key records: {n} repositories filled, {m} skipped"), and the stop counters get `key_events_backfilled` and `key_events_skipped`. Tests: a database with three repositories (one already recorded, one empty, one that needs recovery) → the right rows, the right counts, the server answering while it runs, a kill in the middle and a restart gives the same final state, a second run does nothing.

**T6 — D-1 held by tests.** (a) A source-scan test over the non-test source of every crate: no argument vector or string literal in planeter's code can spawn `prikk trust maintainer remove` (search for `"remove"` in a `trust` context; the driver trait has no such method and must not get one); the test's own text names why (RFC 013 D-1, PK-90). (b) A test over the **argument builder** of the driver: every call it can build for the `trust` verb is `maintainer add`, `maintainer list` or `maintainer check`. Mutation to show: add a `remove` method to the driver and see (a) and (b) fail, then take it out.

## Non-change scope
No page, no JSON field, no message, no catalog text, no Japanese (nothing the owner reads), no creation-form change, no operator command, no `planeter operator`, nothing about D-3 (a keys file in a repository): **do not start it**. No change to the delivery rule, the stage or any refusal. No new dependency; no `unsafe`. No tag, no release, no upload; `cargo publish` only `--dry-run`. The database change is one new table; say so for the upgrade notes (the architect writes them).

## Acceptance criteria
One definition of the bound; creation behaves as before; the table, the reader, the creation recording and the backfill work as described with the tests above; D-1's two tests exist and their mutation was shown; nothing a user sees changed (`git diff --stat` shows no template, catalog or `locales` file); all gates green; CI green on all eight jobs.

## Required evidence and review-request format
Commits (hash → what, by task T1–T6); `git diff --stat`; for T1 the grep for the old constant and the number 64; for T5 the log line and the counters from a real run of the built server over a database with the three repositories above (before and after, and a restart), and the time the pass took with 50 repositories; for T6 the mutation (the failing output, then clean); the gates in a clean worktree with the commands, exit codes, tool versions and the advisory-database HEAD (fmt, floor, pin, clippy, tests with prikk 0.58.0 **three times in a row** and without it, `cargo deny`, `cargo audit`, ENF-2, doc, msrv, the dry run); deviations and open questions (say plainly what you could not show).
