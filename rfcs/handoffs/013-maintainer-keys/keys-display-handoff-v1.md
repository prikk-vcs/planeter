## Change scope

**T0 — Creation checks the id of every carried key (PK-93).** prikk 0.58.0 accepts a wrong key id for a key, which becomes a second entry for the same key. A hostile archive can carry such a pair. Where creation reads the carried keys (the findings, before `trust maintainer add`), require `key_id == key_id_of(public_key)` (`planeter_prikk::keys`, built in the operator work) and `is_public_key`; an archive with a pair that does not match is refused **with the same closed reason a damaged archive already gets** (do not add a new word) and nothing is staged. Tests: a real prikk archive whose carried key's id was altered (build it by editing the findings the way the hostile-archive tests do) is refused and leaves nothing behind; a normal archive is unchanged (the existing creation tests pass untouched). Mutation: the check removed.

**T1 — The repository page shows the keys, always (D-4).** Today `delivered.html` lists the keys the repository trusted *when the last delivery was checked*, and only when a delivery exists. That is a historical fact under a present-tense heading, and it is absent when no one ever delivered. Replace it **on the page** with a section for **the keys the repository trusts now** (prikk's list, through `repo_keys`), shown on the repository page and the history page for **every** repository (the keys are public; a hidden repository's page is already 404 to a stranger), under the existing `<details><summary>` with the count: "Keys this repository trusts ({count})". Each key is one list item: the id (`<code>`), the fingerprint in the eight-group form (`<code>`), and **one sentence of source**, exactly one of:
- creation: "From the repository's creation." — with `backfilled`: "From the repository's creation (recorded on {date})."
- operator: "Added by this server's operator on {date}: {reason}"
- delivery (the reader supports it; nothing writes it until RFC 013 D-3 is built, which is gated — **build only the sentence and a test with a fabricated row**): "Added by a delivery on {date}."
- not recorded: "Source not recorded."
The delivered section keeps its two lines (who delivered, the project's branch) and **loses its key list on the page** (the delivery's own JSON keeps its `trusted_keys` field as it is: that is the API's record of a delivery, named so in the OpenAPI text, and the page and the API now say different things about different moments on purpose: the page says "now"). The reason is **text, never markup** (autoescaped; the stored value is already display-safe; a test with `<script>` and a bidirectional control in a reason shows both are harmless and visible). Dates through the project's date function in the reader's language. **Nothing on the page says retired, revoked, expired, rotated or removed** (D-1).

**T2 — The JSON.** `GET /api/v1/repos/{owner}/{name}/refs` gains `trusted_keys: [{key_id, public_key, fingerprint, source: {kind: "creation"|"delivery"|"operator"|"not_recorded", backfilled?, recorded_at?, delivery_id?, reason?}}]`, in the page's order. The OpenAPI document describes it (and says what `not_recorded` means in one sentence); `api_contract` tests hold the shape; the existing `last_delivery.trusted_keys` is unchanged. A repository whose trust list cannot be read (prikk not answering) answers the route as other prikk-backed fields do today (state which in the report) and never shows a stale list as current.

**T3 — The slots, where a person adopts keys (D-6).** On the creation confirmation page (`stage.html`, where the creator types the fingerprints of the keys to adopt) say, once, in plain words: **"This repository can trust at most 64 keys. Keys cannot be removed yet, so each key you add uses one for the repository's whole life. Adopting these {n} leaves {m}."** (`n` = the carried keys the page offers to adopt; when fewer are chosen, the sentence uses the number the creator has marked, updated by the page's existing mechanism **only if it already has one**; otherwise it states `n` and "at most", and says so: do not add script). The stage report JSON (the findings) gains `keys_max: 64`. The operator's refusal at the bound (its `operator.error.bound`) is the same words.

**T4 — `docs/keys.md` (D-5).** One page, in the project's plain words, for two readers. *A maintainer:* what a trusted key is; where to read the list (the repository page, the JSON); **what you can do** (ask the operator to add a key; rotate by adding the new key, signing new work with it, and leaving the old key trusted; keep several keys); **what you cannot do** (remove a key; mark one retired; make history signed by a key stop counting) and **why** (prikk's `verify` judges the whole history against the keys trusted now: ledger PK-90, PK-91); a **lost key** (leave it trusted; add a new one); **every key lost** (the operator's act); a **stolen key** (no remedy that keeps the history verifiable: stop delivering with the others, tell the people who rely on the repository, wait for prikk's design; a successor repository cannot omit the key either). *An operator:* `planeter operator key add` with the server stopped, the process lock, the refusals and their sentences, the exit codes, that **the reason is shown to everyone who can see the repository** ("if you record a key that was added earlier, say so in the reason"), the bound of 64 and why (the measurement of PK-92 in two sentences), and that the key list is also readable in the JSON. No promise about D-3; one sentence says that adding a key through a delivery is not available. Link it from `README.md` (one line in the docs list), `docs/deliveries.md` ("What a delivery does not do": the bullet on keys points here) and `docs/propose.md` only if it names keys.

**T5 — Messages, English and Japanese.** The few new catalog keys (`repo.keys.*` for the summary with count, the four source sentences and the backfilled variant, the slots sentence; reuse what exists; **no more than about ten**), in the plain words of RFC 012, with the Japanese by the glossary (引き渡す for deliver; no 保持 and no 預かる; 変わる for the verb "change"; ログイン). They ship **flagged until the owner has read them**, together with the 27 `operator.*` messages: give the sheet's `--status` line, and a reading order file for the owner (`keys-0-9-0-reading-order.md`: operator first, then the page's) in the format of `japanese-0-8-0-reading-order.md`. Do not touch `ja.signed`, the `SignOff` or a baseline.

**T6 — Accessibility, and IS-65.** The key list is a real `<ul>` inside the native `<details>`; each item reads in order (key, fingerprint, source); a 64-key list is no wider than the viewport at 320 px (fingerprints wrap: use the project's wrapping class, not a scrolling box). **Run the structural rules (`structure/rules.rs`) over these states, in both languages**: a repository with one key; a repository with three sources (creation, operator, not recorded, plus a fabricated delivery row); **a repository with 64 keys**; a hostile reason; and **make the existing page test of the delivery line (`the_repository_pages_say_who_delivered_only_when_somebody_did`) run the same rules** (IS-65). Add one sentence about the key list to `docs/accessibility.md` (what a reader of a screen reader hears), only if you can say it from what you saw in the saved HTML: say what you did and did not try (no assistive technology was run unless you ran one).

**T7 — D-1 held in the words.** A test over the English and Japanese catalogs: no message whose key starts with `repo.keys.` or `operator.` contains `retire`, `revoke`, `revoked`, `expire`, `rotat`, `remov` (English) or 失効, 無効, 取り消, 退役, 削除 (Japanese) — except the **fixed phrase** "Keys cannot be removed yet" (and its Japanese) where it states the limit; the test lists that exception by key. A page test: the rendered key list in both languages contains none of those words either.

## Non-change scope
No D-3 (a keys file in a repository, gated: do not start it, build no route, no parser, no setting), no new route, no new dependency, no `unsafe`, no change to the delivery rule or the stage, no `trust maintainer remove` of any kind, no change to the operator command's behaviour, no `ja.signed`/`SignOff`/baseline change, no tag, no release, no upload. No new CHANGELOG entry (the architect writes the 0.9.0 notes with the candidate).

## Acceptance criteria
A repository page lists the keys it trusts now with a source sentence for each, in both languages; the JSON carries them; the creation page says how many slots a creation uses; `docs/keys.md` exists and every claim in it is one the tests or the ledger hold; the structural rules pass over every state above (and over the delivery line); nothing says retired or revoked; a carried key with a wrong id is refused at creation; all gates green; CI green on all eight jobs.

## Required evidence and review-request format
Commits (hash → what, by task T0–T7); `git diff --stat`; saved pages and JSON of each state in both languages (the architect reads them); the structural-rules results; the hostile-reason test; the T0 mutation; `planeter-i18n-sheet --status` and the reading-order file; a grep of the repository for "retired", "revoked" in pages and docs with each hit's decision; the gates in a clean worktree (fmt, floor, pin, clippy, tests with prikk 0.58.0 **three times in a row** and without, `cargo deny`, `cargo audit` on a fresh database, ENF-2, doc, msrv) with commands, exit codes, tool versions, the advisory-database HEAD and count; deviations and open questions (say plainly what you could not show).
