## Change scope (measurement only: no product code, no default changed)
1. **CPU-seconds and wall time per gate step.** Run the full gate sequence once, **cold** (a fresh worktree, an empty target directory) inside one `systemd-run --user --scope` per step (or one scope reading `cpu.stat`) so that each step's **CPU time (user + system), wall time, peak memory (`memory.peak`) and the disk it adds** are recorded. One table: step, wall, CPU-seconds, peak memory, GiB added to the target. Note the host's core count, the cap used, and the load from other work at the start (the numbers are for this machine: say so).
2. **Cold against warm.** The same sequence **warm** (the second run in the same worktree) and **warm-shared**: a fresh worktree whose `target` shares the *third-party dependencies'* build outputs with a previous one (try `CARGO_TARGET_DIR` shared across worktrees, and `sccache` if it is installed or can be run without a new dependency of the project: the project adds none; this is tooling on a developer's machine). Report how much of the cold cost is third-party dependencies (compiled once per lock) against the workspace's own crates, and **what a shared dependency cache would save**. State the risks in one paragraph: what a stale or shared cache could hide (a mismatch with the lock, a toolchain change), and why a **release candidate must still be built clean**.
3. **What CI already covers.** From `ci.yml` and `release.yml`, a table: gate step against CI job (same commit, same tools?), and the steps **only a local run can do** (tests that need real prikk and bubblewrap, which the CI runner has none of; the sheet check if CI lacks it; the dry run). From it, the minimum a local review must run, as a proposal.
4. **The tests themselves.** The ten slowest test binaries by wall and by CPU (`cargo test -- --report-time` or `cargo nextest` if available without adding to the project: say which), how many real servers and prikk processes they start, and which could be made cheaper without losing what they hold (do not change any now: list).
5. **Disk.** The size of one gate worktree (by directory: `target/debug/deps`, incremental, `doc`, the dry-run target) and what can be dropped after a run (the dry-run target alone was 2.6 GiB); a **cleanup step** every gate script ends with (`git worktree remove`, `rm -rf` of the scratch by explicit path) that also runs when the gates fail; show it does.
6. **Machine-specific numbers.** List every constant in `tools/` and the scripts that is tuned to this host (800%, 16G, 8 jobs, the worker and confine counts) and propose **derived defaults** (from the core count and the RAM, with an environment override, and a clear message when `systemd-run` is absent) — a proposal in the report, not a change.
7. **A proposal in numbers** for the tiers the architect's amendment defines: for each tier (per commit; a review; a release candidate) which steps, how many times, and the CPU-seconds and disk each would take against today's full set.

## Non-change scope
No product code, no test assertion, no workflow, no default of the load script or the wrapper, no new dependency of the project. Do not touch `docs/SCHEDULE.md`, `docs/STATUS.md`, the ledger, the threat model, `docs/RELEASING.md`. No tag, release or upload.

## Acceptance criteria
Every table above exists with real numbers and the conditions they were taken in; the cold, warm and warm-shared runs are compared; the cleanup is shown; the proposals are in the report and nothing was tuned; the measuring itself is capped and ends with nothing left on disk.

## Required evidence
The tables and the raw `cpu.stat`/`memory.peak` readings; the commands used; the host's cores, RAM and the outside load; the CI coverage table; the slowest-tests list; the cleanup transcript; the proposals; deviations and open questions (say plainly what you could not measure).
