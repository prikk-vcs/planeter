## Change scope

- **T1 — The switch.** In `planeter-auth` and `planeter-web` (dev-dependency), `jsonwebtoken`'s feature `rust_crypto` → `aws_lc_rs` (keep `use_pem` for the test fixtures), at the highest version that builds at MSRV 1.88.0 (the dev team measured 10.3.0, 10.4.0 and 11.1.0 identical: take **11.1.0** unless something in the 11 API changes a line of production code, in which case take 10.4.0 and say why). Rule 1 report in the form "N → M crates (+K); deny: …; audit: …; new licences: …", on the fresh advisory database. **Expected:** `Cargo.lock` 214 → 189; `crypto-bigint`, `rsa`, `p256`, `p384`, `ecdsa`, `elliptic-curve`, `primeorder` and their exclusive dependencies gone; `cargo deny check` and `cargo audit` exit 0.
- **T2 — Retire the ignore.** Remove the `RUSTSEC-2023-0071` ignore from `deny.toml` and `.cargo/audit.toml` (both) **only after** `cargo deny`/`cargo audit` show it unnecessary (`advisory-not-detected`); update the comments (`ISC` is no longer "dev-only": `aws-lc-rs`/`aws-lc-sys`/`untrusted` carry it, the licence is permissive and already allowed); update `docs/dependency-policy.md` (the ignore's entry becomes history; the supply-chain ledger gets the triage record for both advisories in the form RFC 010 D-4 asks: crate path, reachability and how shown, decision, evidence; the line "RustCrypto backend" is replaced).
- **T3 — Promote the matrix and the pin to the repository.** (a) The dev team's scratch **algorithm matrix** becomes a real test in `planeter-auth/tests/` (or `src/oidc.rs` tests): the same 30 rows (valid / tampered payload / tampered signature for RS256/384/512, ES256, ES384, EdDSA; wrong key kind; refused HS256/384/512, PS256/384/512, `none`; wrong audience; expired), test-only keys committed as fixtures with a comment saying they are throwaway. The test pins **behaviour, not the backend**: it must pass on either backend, so the result of any later change of backend is judged by the same 30 rows. (b) The **regression pin** RFC 010 D-4 requires for a crate that parses untrusted input (`jsonwebtoken`): a test under `tests/` that **production code of `planeter-auth` never names `EncodingKey` or `encode(`** (signing exists only in `#[cfg(test)]`), implemented as a source scan that excludes `mod tests`/`#[cfg(test)]` blocks, with a planted-case self-test (a string that names it fails) — this is the standing argument that no private key is ever used by the server, now defence in depth rather than the only defence. (c) A comment on the dependency line in `Cargo.toml` saying why the backend is aws-lc (the two advisories avoided, one provider with the client) and that switching back needs the architect.
- **T4 — Build, release and container evidence.** (a) `cargo +1.88.0 check --workspace --locked` (the MSRV job) passes; note that `aws-lc-sys` and `jsonwebtoken` sit exactly on 1.88.0, so a future bump of either that raises it is caught by that job; (b) `release.yml` builds `x86_64` and `aarch64` natively: run the **rehearsal mode** of the release workflow (`mode: rehearsal`, pushing only to the rehearsal image path, as RFC 010 D-20 allows) on the branch and report that both targets build with the new dependency (the dev team could not test aarch64); if the aarch64 job needs a tool that the runner lacks, stop and report; (c) the container: the `Dockerfile` copies the prebuilt binary — report `objdump -T` (highest `GLIBC_` symbol version) of the new binary against the base image's glibc (bookworm-slim: 2.36) so a binary that cannot run in the image is found now (the dev team found `GLIBC_2.39` for both binaries: if that is real, the image would not start — then this is an existing release defect to be reported at once, not a consequence of this change); (d) ENF-2 (`tools/enf2-symbol-check/check.sh`) exit 0; (e) binary size and clean-build time against `main`.
- **T5 — Documentation.** CHANGELOG (operator-visible: none, except the binary size), `docs/STATUS.md` (IS-54 closed), `README`/`ROADMAP` where they name the crypto backend, the threat model's T-11 line (the architect edits the threat model; give the facts).

## Non-change scope

No change to `planeter-auth`'s production code or the OIDC behaviour; no other dependency change; no ignore added; no version or release change.

## Acceptance criteria

T1's rule-1 report and exit codes; T2's ignore gone with deny/audit 0 on a fresh database; T3's two tests (they pass) plus planted-case self-tests and a mutation (re-adding `encode(` to production code is caught); T4(a)–(e) with evidence; every gate green (fmt, floor, pin, clippy, both test runs, deny, audit — **now both must be 0** — ENF-2, doc), CI green on the commit.

## Prohibited shortcuts

No ignore; no change to the OIDC verifier to make the test pass; no edit of `deny.toml` beyond removing the retired ignore and comments; no skipping the aarch64 evidence.

## Required evidence and review-request format

Commits (hash → what, by task); the rule-1 report; the matrix and pin tests; the rehearsal run's link and per-target result; the glibc finding; every gate with command and exit code and the advisory-database HEAD; deviations and open questions.
