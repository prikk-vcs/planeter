# RFC 010 — IS-69: tests that assert a number of milliseconds must assert what they mean — Implementation Handoff (v1)

| | |
|---|---|
| Document | Four tests in this release cycle failed once each under host load and passed straight after: the ETXTBSY race of the stand-in scripts (fixed), the kill table's flag read before the recovery thread ran (fixed), the lease test that counted reads in a fixed time (changed), and **`a_light_read_never_waits_behind_a_waiting_heavy_one`** (`planeter-web/tests/admission_gate.rs:401`: "waited 102 ms", threshold 100 ms, in the architect's run at a host load above 70). The last is untouched and still wrong in kind: what it holds is an **ordering** (a light read is not queued behind a waiting heavy one), and it asserts a number. A release runs the whole suite in its `gates` job; a test that fails by load costs a re-run at the worst moment and teaches people to ignore red. This handoff changes the assertions that mean an ordering into assertions that state the ordering, and leaves the ones that are only a guard against a hang. |

## Change scope
1. **The inventory (do it first and show it).** Every assertion in a test that compares a measured duration with a constant (`elapsed()`, `Instant`, `took`, `waited`, `Duration` in an `assert!`): file, line, the constant, **what the test means by it**, and a class:
   - **A — a guard against a hang** (a generous bound, five seconds or more, "it returned"): keep; if it is under five seconds, raise it to a bound no loaded host reaches (say the number and why), and say nothing else.
   - **B — an ordering or a non-wait** (something must happen before, or without waiting for, something else: the admission gate's light read, the lease's readers and writer, the fetch's two `< 500 ms`): **replace the number by the ordering.** Make the thing that must come first observable (a channel, a counter, a latch, the order in which two tasks finish, a flag set by the earlier task) and assert that. Where the test must hold a heavy task busy to make the ordering matter, hold it with a latch the test releases, not with a sleep of a given length.
   - **C — a deliberate timing property** (a wait of at least N ms because a deadline or a backoff is the thing under test, e.g. `>= 900 ms`): keep the lower bound (it cannot fail by load) and give any upper bound a margin that scales with a measured baseline taken in the same test (the time of the same operation without the load), not a constant.
2. **The conversions of class B**, test by test, each with a one-paragraph note of what the old assertion could not distinguish (a slow host from a real queue) and what the new one does. **A mutation for each converted test, shown failing once and reverted:** make the property false (for the gate: make the light read wait; for the lease: make the writer starve) and see the converted test fail, **and with the property true and an artificially slow host (a `sleep` or a busy loop inserted before the assertion's measurement) see it still pass**.
3. **Do not change what a test holds, only how it says it.** If a test turns out to hold nothing once the number is gone, say so and propose its removal; do not remove it.
4. **A repeat-under-load script** at `tools/` or `scripts/` (your choice; a plain `sh`) that runs the changed test files N times with `cargo test` under a CPU load generated by `yes > /dev/null` workers (as many as cores) and reports the failures; run it and show **100 repetitions of each converted test: 0 failures**, and the same script on the unconverted tests at `c`-before showing what it was able to catch (if it catches nothing, say so: it is evidence about the script).
5. **Not in this handoff:** a scheduled CI job (the architect decides after reading the script's results); the ETXTBSY and recovery-thread fixes (done).

## Non-change scope
No product code; no change to a bound that is a product rule (the admission pool sizes, the lease timeouts); no catalog text; no new dependency; no tag, release or upload. Do not touch `docs/SCHEDULE.md`, `docs/STATUS.md`, the ledger, the threat model.

## Acceptance criteria
The inventory is complete and classified; every class-B test asserts an ordering and its mutation was shown; 100 loaded repetitions are green; no new flake in three full runs with prikk 0.58.0; all gates green; CI green on all eight jobs.

## Required evidence and review-request format
The inventory table; commits (hash → what); for each converted test the paragraph, the mutation (failing output, then clean) and the slow-host check; the script and its results; the gates in a clean worktree (fmt, floor, pin, clippy, tests with prikk 0.58.0 **three times in a row** and without, `cargo deny`, `cargo audit` on a fresh database, ENF-2, doc, msrv) with commands, exit codes and the advisory-database HEAD; deviations and open questions (say plainly what you could not show).
