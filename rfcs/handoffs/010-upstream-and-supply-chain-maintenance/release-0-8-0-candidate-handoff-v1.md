## Non-change scope
No tag; no GitHub release; no crates.io upload; no ghcr change; no feature or fix beyond the files named; no dependency change (T5 by table); no change to a default; **no catalog text change; no Japanese sign-off; no baseline edit**; no change to the delivery engine, API or client.

## Acceptance criteria
T0–T8 with their evidence; the candidate commit on `main`, everything green, **the rehearsal green on both architectures with the new BuildKit pin**; the CHANGELOG readable as release notes without editing facts; the counts of unread Japanese stated in the notes and equal to the tool's; the reading-order file written.

## Prohibited shortcuts
No tag, no upload; no "publish" step run even as a test; no edit of a historical CHANGELOG entry; no weakening of a gate; no `ignore`; no sign-off record for text the owner has not read; no BuildKit move without the full D-9 record.

Commits (hash → what, by task; T0 first); the T0 record (old/new tag and digest, annotation check, notes, advisories) and the rehearsal run link with the per-job result and the log lines; T1's status lines, the sheet header and fingerprint, the reading-order file's counts; the `cargo package --list` summaries and the dry-run result; the pins table; T7's saved pages, JSON and transcripts and the kill-and-restart log; every gate with command, exit code, tool versions (prikk, cargo, cargo-deny, cargo-audit) and the advisory-database HEAD; deviations and open questions.

## Addendum (2026-11-21, SCHEDULE D-101) — one change to T4
The `sync seal` figures in `docs/deliveries.md` (and wherever the CHANGELOG states them) carry **their shape and storage**: "each claim adds one new file, so the tree ends with N paths; measured on an encrypted btrfs disk: 100 claims 1.0 MiB; 1,000 claims 7.1 MiB; 10,000 claims 183.6 MiB and 670 s; read about 23 KB a claim"; and these three sentences, as measured by the architect on 2026-11-21 (ledger PK-88): *the memory of `sync seal` grows with the number of claims*; *with a tree that stays the same size it grows linearly (68 MiB at 10,000 claims)*; *with a tree that gains a file per claim it grows faster than linearly (181 MiB at 10,000 claims)*. No other claim about memory or speed. The time depends on the disk (about 90 s on tmpfs, 670 s on an encrypted btrfs disk for the same work).
