# RFC 004 — Transport — Implementation Handoff (v2, part 11): the client's "prikk was not found" that was not true, and the flaky flows tests

| | |
|---|---|
| Document | The dev team's gate run saw `planeter-client`'s `flows` tests fail under load (four different tests, three different symptoms), unexplained, passing in CI and when the machine was quiet. The architect read the code. **Two real findings, one product bug and one probable test race:** (1) `Prikk::check` (and `Prikk::run`) turn **any** failure to start prikk into the sentence "prikk was not found. Install prikk 0.54.0 or later…" and drop the cause (`check` even drops the `io::Error`): a user whose prikk is there but cannot be started (permission denied, `Text file busy`, a broken interpreter in a wrapper, out of processes) is told to install what they have installed — a lie, in the program that exists to be plain and true. (2) The tests start prikk through a `#!/bin/sh` wrapper that `home_wrapper` **rewrites on every `client()` call**, in a process where ~25 test threads fork concurrently: on Linux a script that has just been written can be `exec`ed while another thread's fork still holds a copy of its write descriptor — `ETXTBSY`, reported by `Command::output()` as a spawn error, which the client then prints as "not found". That explains the two "prikk was not found" failures; it does not by itself explain the other two (an archive "not readable by your prikk", a key "not carried") — they may be the same race (a wrapper executed while truncated by the next rewrite of the same path within one test, or a stub-server ordering), or something else: find out. |

## Change scope

- **T1 — Tell the truth about a prikk that cannot be started (product).** Distinguish by `io::ErrorKind` at every place the client spawns prikk: `NotFound` → the existing "prikk was not found…" sentence; **anything else** → a new sentence in both languages: "prikk was found but could not be started: {reason}." with the next step ("Check that it runs by itself: prikk --version."), the OS error as the `{reason}` (`Text file busy`, `Permission denied`) and also in `--verbose` detail; `check` keeps the `io::Error` as the detail (it drops it today). An unreadable `--version` output stays its own case ("prikk did not say which version it is: {first line}"). Tests: a stand-in that is not executable (permission denied), a directory, a script with a broken interpreter, and a missing program each give their own sentence; none says "not found" except the last. New messages in both languages (catalog tests; Japanese draft row in the next addendum).
- **T2 — Reproduce, then fix the tests (a measurement before a change).** First reproduce deterministically: run `cargo test -p planeter-client --test flows` repeatedly under a memory-limited scope **with artificial load** (for example `taskset -c 0` plus a CPU burner you start and **stop by recorded PID**, not `pkill -f`), count failures per symptom, and record the real `io::Error` (T1 makes it visible in the failure text). Then fix **what the evidence shows**, preferring these designs in this order: (a) **do not write executables in the test process at all** — the interactive flows need injected stdin/tty state, but the wrapper only needs a per-test `HOME`: instead let the tests set the HOME for the child through the same `Ctx.env` hook the client already reads to find its state directory (the child is spawned by the client's `Prikk` runner, which would pass `HOME`/`XDG_CONFIG_HOME` to the child **only when the context supplies them** — a small, honest change: the runner applies the context's environment to the child instead of inheriting the process's), which removes the wrapper and `PLANETER_CLIENT_PRIKK` from the flows tests; or (b) create each test's wrapper **once**, before the test starts any thread of its own, never rewrite it, and wait for it to be runnable as `72eb228` does. Whichever it is, the other two symptoms must be explained by the evidence or stay listed as **open** with what was tried.
- **T3 — A guard so it cannot come back unseen.** A test-only helper `retry_spawn`-style hiding of the race is **not** acceptable; instead add a stress test target (ignored by default, run by hand and by a scheduled CI job if you can) that runs the `flows` suite N times in parallel under `taskset`, and document in `docs/client.md` "tests" how to run it. The scheduled job is optional; report if you add it.

## Non-change scope

No change to the client's commands, bounds, exit codes or the server; no retry loop in product code to hide a race; no new dependency; no `unsafe`; no version or release change.

## Acceptance criteria

T1's sentences and tests; T2's reproduction numbers before and after (failures per 100 parallel runs under load, per symptom), the chosen design and why; all `flows` tests pass 100 of 100 runs under the same load; the other two symptoms explained or listed open; every gate green (fmt, floor, pin, clippy, both test runs, deny and audit 0, ENF-2, doc), CI green on all three systems.

## Prohibited shortcuts

No `sleep`-based waits as the fix; no silent retry; no `pkill -f`/`pgrep -f` patterns that can match their own shell; no touching other projects' processes; no run outside a memory-limited scope.

## Required evidence and review-request format

Commits (hash → what); the before/after counts per symptom; the design chosen with the evidence; the new messages; every gate with command and exit code and the advisory-database HEAD; deviations and open questions.

## Addendum (same day): the architect's own gate run reproduced it, and a third suspect

My gate run on `6269de2` (a clean worktree, load average 19–32 from other projects) failed **two** `flows` tests (`an_advertisement_without_numbers_falls_back_to_continuation_and_says_so`, `a_lower_number_or_the_same_number_with_another_state_is_refused_before_anything_is_downloaded`), both at `flows.rs:530`, **the initial `clone` inside `fetching()`**, with two different texts: "The request to the server failed" and "The downloaded file is not a repository archive your prikk can read" (`left: 3`/`left: 4`, exit codes 3/4). Re-run alone at load ≈ 16 the file passed 9/9. So the flake is real, load-dependent, and **a flaky gate is a defect of the project, not of the machine**: my review has to either report a red run or rerun until green, and neither is acceptable for a gate.
**Third suspect (the test server, `tests/common/mod.rs::Server::start`):** after `write_reply` the connection thread does `send_close_notify`, `flush`, and then **drops the socket**; the server has read only the request head (one byte at a time) and may still have unread bytes in its receive queue (the client's own TLS close alert, post-handshake records). On Linux, `close()` with unread received data sends **RST instead of FIN**, and an RST can discard response bytes the client has not yet read: the client sees "the request failed" or a **truncated** archive ("not a repository archive"). It needs exactly the timing a loaded machine produces and it affects the largest body (the archive) in the first request of a flow. This fits both texts and the failing step. **Fix to try first, with the same reproduction as T2:** after writing, `tcp.shutdown(Shutdown::Write)` and then **drain the read side until EOF or the 20 s timeout** before dropping (a graceful close), in `Server::start` and in `examples/tls_terminator.rs` if it has the same shape; and make `read_request` read the head in chunks rather than a byte at a time. Report the before/after counts per symptom. The three suspects (ETXTBSY on the rewritten wrapper, the RST close, and whatever else the evidence shows) may each explain some of the four symptoms; the acceptance criterion is unchanged: 100 of 100 parallel runs under load pass.
