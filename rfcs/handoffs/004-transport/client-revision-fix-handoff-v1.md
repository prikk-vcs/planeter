# RFC 004 part 10 — `planeter-client propose --proposal ID` is refused by the real server — Implementation Handoff (v1)

| | |
|---|---|
| Document | The 0.7.0 candidate's end-to-end look (T7) found that **adding a revision to an existing proposal with `planeter-client propose --proposal ID` cannot work against the real server**, in 0.5.0 and 0.6.0 as well. The client always sends `"target_ref"` in the upload's metadata; the server refuses `target_ref` (and `title`, `description`) together with an existing proposal id (`MetaError::FieldsForExistingProposal`, `crates/planeter-transport/src/propose.rs`), which the web layer shows as `400 invalid_request`, and the client prints its generic "the request is malformed" line. The client's tests use a mock server, so nothing caught it; the second revision of the file-by-file view could only be shown by a script. The server is right (a revision belongs to the proposal that exists; its target does not change); **the client is wrong**. It is a defect of a documented feature, so it is fixed **before the 0.7.0 tag**, in the client only. IS-59 (SCHEDULE D-83). |
| Status | Assigned 2026-11-17. |
| Basis | `release-0-7-0-candidate-review-request.md` finding 1 and `t7/propose/revision-2-by-the-client.txt`; `crates/planeter-client/src/commands/propose.rs` (the metadata); `crates/planeter-transport/src/propose.rs` (`ProposeMeta::validate`); `crates/planeter-web/tests/client_e2e.rs` (the real client against the real server); `docs/client.md`. |
| Audience | Dev team. Return a short review-request package. The 0.7.0 candidate becomes the head of this work (T4). |

## Change scope
1. **The client.** When `--proposal` is given, the metadata carries `proposal`, `base`, `declared_patches` and `client` and **none** of `target_ref`, `title`, `description` (the client already omits the last two). When `--title` or `--description-file` is given together with `--proposal`, the client refuses **before any network call** with one plain sentence in both languages saying that a revision keeps the proposal's title and description (write it in English; the Japanese is yours, plain, no 保持/預かる, flagged as new); today such a combination is sent and refused by the server. `--ref` still names the local branch to send; say in the help text of `propose` (both languages) that with `--proposal` the work is added to that proposal's own target (check the existing help sentence and change only what is untrue).
2. **A test with the real validation** (this is the missing test): in `planeter-web/tests/client_e2e.rs` (or the file that already runs the built client against the real server and real prikk) send **two revisions with the real client**: the first with `--title`, the second with `--proposal <id>` after more work; assert the second is `201`-equivalent (the client's success line), the proposal shows **two revisions**, the second revision's added patches are only the new ones, and the changes page of revision 2 answers. Add the refused combination (`--proposal` with `--title`): refused locally, no request reached the server (count the server's requests). **Mutation:** put `target_ref` back into the metadata → the test fails with the server's refusal (show it once). Keep the mock-server tests; add to their metadata assertion that `target_ref` is absent for `--proposal` and present for a new proposal.
3. **What a person sees when the server does refuse a proposal's metadata.** The client printed only "the request is malformed" because the server's reason (`fields_for_existing_proposal`) did not reach the person. Report (do not fix unless it is one line in the client's existing error mapping): does the JSON error body of that 400 carry the reason, and does the client show it with `--verbose`? If the reason is in the body and the client drops it, show it in the verbose detail; say in the report what you found.
4. **Evidence of the old behaviour** (before the fix) with the 0.6.0 client binary against the new server: one run's output saved, then the same with the fixed client. The server is **not** changed (the 0.5.0/0.6.0 clients stay unable to add a revision; the CHANGELOG says so and to upgrade the client).
5. **Docs and notes.** `docs/client.md` (what `--proposal` does and that title and description are fixed by the first revision); `CHANGELOG.md` `[0.7.0]`: in "For people who use it" one entry — adding a revision with `planeter-client propose --proposal ID` works; **in the 0.5.0 and 0.6.0 clients the server refused it** (so a person who needed a second revision had to open a new proposal), upgrade the client; no change to the server or the API. Do not touch any other entry. The client's version is the workspace's (0.7.0 already).
6. **The client changed, so the stress target runs** (`PLANETER_STRESS_RUNS=20`, memory-limited scope) and its result is reported; CI on three systems must pass.
7. **The candidate.** The release candidate is this handoff's head: re-run the candidate gates on it (the full set of the 0.7.0 handoff T6: fresh advisory database, pinned tools, tests with prikk and without, ENF-2, doc, msrv, the dry run with a fresh target, sheet `--check` with its count: the new refusal sentence adds Japanese messages: report the new count and update the CHANGELOG's count sentence to the tool's line), and redo T7's revision 2 **with the real client** (no script): save the proposal page, the changes page and the JSON of revision 2 as in T7. State the final candidate hash.

## Non-change scope
No server change; no API change; no new setting; no other client behaviour; no pin moved; no rehearsal (the release chain is unchanged); no sign-off data; no version change.

## Acceptance criteria
The real client adds a second revision against the real server and the test shows it; the combination refusal is local; the mutation is caught; the stress run and all gates green; CI green on three systems; the CHANGELOG entry; the final candidate hash and the saved pages of revision 2.

Commits (hash → what); before/after outputs (0.6.0 client against the new server; the fixed client); the test table with the mutation; the answer to task 3; the stress run; the sheet header, count and fingerprint; every gate with command, exit code, tool versions and the advisory-database HEAD; the saved pages; deviations and open questions.
