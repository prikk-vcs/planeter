## Part A — measure (before any change; the stop rule applies)
1. **`sync accept` cost on 0.58.0** — the model's table of PK-68/PK-69/PK-75: `VmData` (the quantity `RLIMIT_DATA` limits, sampled from `/proc/<pid>/status`), RSS, wall time, fsyncs (`strace -c` or the harness's way) for: one large blob at 1, 10, 25, 50, 100 and **250 MiB** (random and compressible; **three runs each for the 250 MiB**, prikk saw 1,005 MB ten times and 1,256 MB once), 100 × 1 MiB, 10,000 one-file patches (7.4 MB), 1,000 patches, 1,000 blobs in one patch. For each: `VmData / artifact`, `VmData / largest object`, and the **fit** (`a × artifact + b × largest object + c`) like part 4b's. Compare each with 0.57.0 on the same artifact. **STOP-A** if any shape's `VmData` is **above 7.0 ×** the artifact (the present model) on 0.58.0.
2. **The delivery's own prikk calls on 0.58.0:** the stage (`archive verify`, `archive import --adopt`) at the small, 63 MiB and 259 MiB lineages of the 0.8.0 measurement (`model-b-measure-v2-logs`): `VmData`, RSS, time, bytes read; the creation cost model's `verify_cost` 3.0 × and `import_cost` 6.0 ×: do they still bound them? (The import now reads more: 40 × 1 MiB, 85 → 126 MB.) `log`, `verify`, `branch` on the staged repository as the engine reads them (time, `VmData`). **STOP-B** if the import's `VmData` exceeds 6.0 × the archive on any lineage.
3. **The re-accept of a delivery on 0.58.0:** re-run the engine's three-proposal scenario and the **1,000-patch** re-accept; report the time and fsyncs per patch against 0.57.0's (9.4 ms and ~15 fsyncs per patch measured: PK-84); the delivery's lease window (`confirm` end to end) small and 63 MiB.
4. **`sync seal`, the maintainer's side:** the real flow of the 0.8.0 measurement (a maintainer seals what the forge accepted, `sync seal --claims`, then `archive export`): at 100, 1,000 and, if it takes under 30 minutes, **10,000 claims**: time, read bytes, peak memory on 0.58.0 (the letter says linear, 21 KB read per claim). This is the figure the maintainer documentation may state; report it honestly with the host's load.
5. **`extract` and the 0.7.0 changes view:** `provisional` for a repository made by creation (`archive import --adopt`), for one made by `init` and `sync accept` only, and for a delivered one; whether `--allow-full-replay` is still needed anywhere the view uses (try without it on each); the `extract` cost table of `admission.rs` (the 77-row read table and the `extract` rule): re-run the measuring scripts of the 0.57 re-baseline on 0.58.0 (`t5/`, `extract/`) and report any row that **moved by more than 5 %** or tripped.
6. **What the readers meet:** the new `verify` finding `PRIKK-VERIFY-REF-PUBLICATION-IN-FLIGHT` (info, exit 0): produce it for real if you can (a `tag create` loop beside a `verify`, as the letter describes) and show what the driver's `verify` reader does with it (it must read it as information, never as a failure and never as an unreadable report); the changed truncated-artifact sentence (`unexpected end of patch-exchange artifact: …`): which of our texts, tests or the closed lists quote the old one; the active-lock-before-validation: a second `sync accept` / `sync seal` / `commit` meeting `lock conflict` during an accept (exit 1 and the words): confirm that `classify_failure` calls it **not refused** and the repository is not flagged (the store signature rule must still decide: show the case); an artifact file that changes between the two reads (hand-made: the words; the driver copies the artifact into its own accept directory so this should not occur: confirm); `unlock --lock <path> --force` still clears the stale locks of a killed accept and `--yes` alone no longer does for an `unknown` holder (the recovery procedure never passes `--yes`: show the unit test).
7. **Format and refusals:** `prikk format` of a new repository (still 8?), the 0.57 floor tests' refusal text for 0.57.0 once the floor is 0.58.0.

## Part B — adapt (only if no STOP)
B1. **The floor to 0.58.0** in every place the 0.57 re-baseline touched (`MIN_PRIKK_VERSION`, `planeter-client`'s floor, `release.yml`, `ci.yml`, the `Dockerfile` `PRIKK_VERSION`, README/docs, stand-in prikks that print their version, the floor tests, `floor-check`): the 0.57 re-baseline's review request is the list. The server refuses to start on 0.57.0 with the existing sentence; the client stops at its own message. **The release asset's checksum** for 0.58.0 is verified by the workflows' existing step.
B2. **The two tests** assert the new truth (not provisional where the import recorded the history; keep one test that **is** provisional where it still is, found in A5; if none remains, the test of the statement `changes.statement.provisional` uses an injected answer as the hostile tests do). No weakening.
B3. **The cost models** (`MEASURED_ON` = 0.58.0): propose's `BYTES_TENTHS`, `PER_OBJECT_BYTES`, `BASE_BYTES`; creation's `verify_cost`/`import_cost`; any admission row that moved. **The rule that decides the constant (so no round trip is needed):** the new constant is **1.1 × the worst measured ratio** over the shapes of A1/A2, rounded up to a tenth, **never below 4.5 ×** for accept (the largest object is unknown before prikk reads the artifact, so the whole artifact is assumed to be one object: 4.06 × measured for one 100 MiB blob, 5.0 × for prikk's outlier) and never above the present value; the ceiling factor (1.5 ×) does not change; the per-object term is re-fitted the same way. Every changed constant is **its own line of the report with the measurement behind it**; the doc comments of the models, `docs/propose.md`/`docs/RELEASING.md` (the memory sentences: "a 100 MiB proposal needs about 0.7 GiB": recompute) and the start-up line's numbers are updated; the tests that pin the cost (`accept_admission`, `admission`) follow; a table test requires the new `MEASURED_ON`.
B4. **The readers:** the `verify` reader reads the new info id as information (test with the real output if produced, else a fixture of the letter's shape); any closed list or test that quoted the old truncated-artifact sentence follows (both sentences are accepted by whatever matches on it: say which); nothing else changes.
B5. **Docs and CHANGELOG:** `[Unreleased]` gets **one entry**: the floor moves to 0.58.0 and why (accept memory and time, `sync seal` linear, imports that record history, `provisional` less often), with the new numbers of A1/A3/A4 stated as measured; "Upgrading": install prikk 0.58.0 or later (the image carries it). `docs/client.md`/the maintainer documentation: the `sync seal` figure of A4, as measured. Nothing is said about speed that A4 did not measure.
B6. **The letter.** Do not write to prikk. List in the report anything the architect should ask them (for example the two residuals of their §5 as they affect a forge that tags while it seals: planeter does not tag).

## STOP rules
**STOP-A**, **STOP-B** above; **STOP-C:** any test that fails on 0.58.0 other than the two named, or any Part A finding that changes the failed-accept classification, the stage's rule, or the delivery's kill points: report it with the evidence and make **no** Part B change.

## Non-change scope
No behaviour of the product beyond the floor, the constants, the two tests and the reader; no pin, no version, no sign-off data; no catalog text (a new message would need the owner's reading: if one is needed, say so and stop); the delivery engine and API are not touched except by the cost constants they read.

## Acceptance criteria
Part A's seven items answered with commands and outputs; the stop rules answered; Part B: the floor in every place (`floor-check` 0), the two tests re-baselined, the constants changed per the rule with their measurements, the reader's test, the CHANGELOG entry; all gates green with prikk **0.58.0** on PATH (the real-prikk tests) and without prikk, **and** the suite also run with the private 0.57.0 first on PATH (the floor tests aside: list what fails and why, expected: the floor tests); `cargo deny`/`cargo audit` 0 with the pinned tools; the dry run is **not** expected to pass at 0.7.0 (D-82: say so); CI green (the runner has no bubblewrap: stand-in tests `Sandbox::Unconfined`).

## Required evidence and review-request format
Commits (hash → what); Part A tables (shape → 0.57.0 → 0.58.0 → ratio; the fit; the stage; the re-accept; `sync seal`; `extract`; the readers' cases); the constants before → after with the measurement; every gate with command, exit code, prikk and tool versions and the advisory-database HEAD; deviations and open questions.
