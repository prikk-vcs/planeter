## T1 — the engine: a landed revision's change set from the sealed history
In `planeter-transport::changes` (the engine of 0.7.0). When the chain read of a revision finds that its claims are **not pending** (today `ClaimNotHeld`), do not answer at once: ask **the landing observation's own function** (reuse `observe_landing` / the log reading of `proposals.rs` with `FOLLOWED_REF`; **no second definition of landed**) where the revision's patches are:
1. **All of the revision's patches are in blocks of `heads/main`** (the revision's own patch ids: its `added_patch_ids` as stored, **plus** the patches it declared that were already held — use the revision record's declared set where the stored set is empty; say which fields you used and why, with the case of a revision that adds nothing new): find the blocks that carry them from `log --ref heads/main --format json` (`blocks[].patch_messages[].patch_id`, `parent_block_ids`, the whole chain read with the engine's existing bounded reader: never a fixed limit). If they lie in **one run of consecutive blocks of the first-parent chain** (every block between the first and the last carries only patches of this revision; merges and interleaved blocks of other work are *not* consecutive), the **before** is the first block's parent and the **after** is the last block: `extract --ref <block>` for each (the existing sandboxed extraction, admission, bounds, `provisional` copied from the report; `--allow-full-replay` as the engine already passes). The comparison, the display safety, the diff, the cache (keyed by the two block ids — content-addressed, never stale), the single flight, the waiter bound, the 30 s wall: **all the existing code**. The answer's `compared` carries `before_block`/`after_block` and a new boolean **`landed: true`**; `rebuilt` stays true (the files are rebuilt by prikk from sealed patches).
2. **Some of the revision's patches landed and some did not** → a new closed reason **`partly_landed`** (HTTP 409, additive to the API's closed list and the OpenAPI enum): "Some of this revision's work has landed in the project's branch and some is still waiting here, so its changes cannot be shown as one change." hint: "Look at the project's history for what landed. The rest is still held for review." (English; Japanese by you; no 保持/預かる; no *claim*, *chain*, *block*, *landed* is the project's own word on the proposal page: keep it).
3. **All landed but not one run** (reordered, interleaved with others, a merge): the existing `not_one_change` with its sentence (the patches do not form one single sequence).
4. **None landed and not pending** (the work left the queue another way, or the artifact is gone): the existing `claim_not_held` — keep the sentence, but its example ("for example because it arrived as signed history") is now less true than ever: change **only** that clause to read "for example because it was removed from the queue" **if** no case remains where signed history is the cause; otherwise leave it. State which.
5. A revision of a **landed proposal** and a revision of an **open proposal whose first revision landed** (P3 of the measurement: r1 landed, r2 and r3 open): r1 → the landed view; r2 and r3 → `claim_not_held`/`partly_landed` as the facts say (their claims are pending **or** their patches are partly landed): test all three.
6. **The page** (handoff-2 pages): a statement line for `landed: true`, English "These changes have landed: they are part of the project's branch." (exact; the Japanese by you), placed before the existing statements; the reason page for `partly_landed` through the existing reason-page template; the proposal page's link text for a landed revision is unchanged ("See the changes in revision N"). The structural, stylesheet, glossary, plain-words and language-rule tests cover the new states in both languages; the scan for internal words extends to the new messages.
7. **The API** (`GET …/revisions/{seq}/changes[…]`): the additive `landed` field and the `partly_landed` reason in OpenAPI and the contract tests; nothing else changes shape.

## Tests (real prikk 0.58.0 + the real server; each hostile or lifecycle case with a **mutation** shown failing once)
- The measurement's scenario through the real client and a real delivery: **P1 (one commit) landed → its view is the files P1 added; P3 r1 landed → its view; r2/r3 → their reasons; P2 open → its ordinary view; P4 (three commits sealed together by the maintainer) landed → the three files, one run of blocks**; the numbers (files, lines) equal a `diff -r` of the two extracted trees.
- Non-consecutive: the maintainer lands P5's two patches with another maintainer commit between them → `not_one_change`; a landed revision whose block is the **first** block of the history (no parent: "before" empty, say so as the 0.7.0 view does for a root); a revision whose patches are split across two deliveries (landed in the first only → `partly_landed`, after the second → the view).
- The cache: the second request is served from it (one extraction pair); a landed view cached under the two block ids survives a later delivery (it is content-addressed and the blocks never change); the old pending-claims cache entries are not read for a landed revision (a mutation that reads them → the test fails).
- Hostile: the engine's existing hostile cases (names, links, long lines, depth) hold through the landed path — one real-prikk run with a symlink-free adversarial name set is enough because the comparison code is shared; plus: **a patch id that appears in two blocks** (a repeated patch; construct it if prikk allows: say if it does not) does not make the view show a mix; **the log of `heads/main` is larger than the window** (the observation's `PLANETER_OBSERVATION_BLOCKS` window: a revision landed longer ago than the window answers the existing "unknown" way: say what the page shows, and that it never claims a landed view it cannot prove).
- Authorization and 404 equality: unchanged routes (the IS-14 table, the 404 byte equality over the landed case too).
- Mutations: the "consecutive" test removed (a patch from another block is silently included) → fails; `landed: true` always false → the page test fails; the landing observation replaced by "any published ref" → the extra-branch test fails; `partly_landed` answered as `claim_not_held` → fails.
- Logs/counters: one counter per new outcome (`landed_ok`, `partly_landed`) in the `Metrics::changes` style; the canary (no file or branch name in the log) holds.
