## T0 — three amendments to the engine (before the routes; small, each with its test)
1. **Rule 5 is "no ref changed", not "`heads/main` unchanged"** (engine review, deviation 2). `nothing_to_deliver` only when **every** published ref of the stage has exactly the live tip and no ref is added. A delivery that only adds a branch is acceptable (`new_tip` = the unchanged `heads/main` tip, `refs_added` lists the branch). The report's `new_blocks` counts the distinct blocks of the staged chains that the live repository does not have (all refs). Update the rule's table (the `dev` row against S1 is now ACCEPT), the report, the docs of `rule.rs`, and RFC 008 D-3 rule 5 (one sentence; the architect reviews the wording: "the delivery changes at least one ref").
2. **The stage directory takes the live repository directory's mode** (deviation 7): before the exchange, `chmod` the staged repository to the live directory's mode and check that its owner is the server's user; test with a live directory at 0750 (and with another mode); a mismatch of owner stops the delivery `failed(exchange_failed)` before any exchange.
3. **A recovery run completes a delivery** (deviation 4): when the existing recovery procedure clears a `delivery_unfinished` flag, it calls the engine's `resume` for that repository (one place, in the recovery completion; and `reconcile_at_start` still does it at start). A test: kill a `reaccepting` delivery, run the recovery by its route/procedure (not by a restart), assert the delivery ends `done`.

## T1 — the API (bearer token only, like propose; `Action::MergeSeal`)
Routes (constants in `api.rs`, in the authorization table with class `Authorized` for `MergeSeal` on the repository, probed by the IS-14 enumeration: a stranger, a reader, a contributor, a token whose scope is capped below merge-seal, and a hidden repository get the answers the table says; **a hidden repository and an unknown delivery give one 404, byte for byte**):
- `POST /api/v1/repos/{owner}/{name}/deliveries` — the body is the archive, **the same upload shape and the same edge limit as repository creation's import** (`PLANETER_IMPORT_MAX_MB`; `has_own_body_limit` extended for this route; the body is never read when the caller is refused: authorization, the repository's state and the stage limits are decided before the first byte, as propose does). Answers `201` with the **delivery view** (below) once staged and reported (the stage and the rule run inside the request, bounded by the engine's deadline; if they take longer than **25 s** the route answers `202` with the view in state `staged` and the client polls). Errors in the project's one shape `{code, message, hint}` and the engine's closed lists: `too_large` 413, `stage_limit` 422, `busy` 409, `needs_recovery` 409, `unavailable` 503 (with `Retry-After`), `ceiling`/`timed_out` 503. A refused **report** is not an HTTP error: it is a `201` view whose `report.verdict` is `refused` with its `reason` (the maintainer asked a question and got an answer).
- `GET /api/v1/repos/{owner}/{name}/deliveries/{id}` — the delivery view (below); the same principal only (another maintainer's delivery is a 404).
- `POST /api/v1/repos/{owner}/{name}/deliveries/{id}/confirm` — runs `confirm` **detached from the request** (a dropped connection must not abort an install: it is journaled and recovered, but it should simply finish); waits up to **25 s** and answers `200` with the final view (`done`) or `202` with the view (`reaccepting`, the client polls `GET`). `not_confirmable` 409, `expired` 410, `busy` 409 (the delivery stays `reported`), a failed install: `200` with `state: failed` and its reason (the request worked; the delivery did not), and the `delivery_unfinished` case as `202`/view with `needs_recovery: true`.
- `DELETE …/deliveries/{id}` — `cancel` (a staged or reported delivery; `204`).
- **The delivery view** (one schema in OpenAPI, `DeliveryView`): `id`, `state` (the nine states, closed), `started_at`, `updated_at`, `report` (`verdict`: `acceptable | refused`, `reason` (closed list, null when acceptable), `old_tip`, `new_tip`, `new_blocks`, `refs_added`, `proposals_stay`, `proposals_land`, `proposals_cannot_be_kept` (each a list of `{id, title}` — titles through the same output path as other API titles; no other proposal data), `trusted_keys` (`key_id`, `fingerprint`), `archive_bytes`), `failure` (`reason`, null), `needs_recovery`, and a `message` + `hint` pair **in the caller's language** that says in plain words what the state means and what to do next (see messages). Nothing about paths, prikk output or file names.
- Rate limits: the transport limiter the propose routes use (per address and per person); the stage limits are the engine's.
- Counters and logs: the engine's; the routes add none that carry a name.

## T2 — the repository page and the proposal wording
- **The line** (RFC 008 D-4), on the repository's home page and the history page, **only when the repository has a `done` delivery**: "Delivered by {name} on {date}: signed by a key this repository trusts and checked by prikk." with the date in the project's ISO 8601 UTC form, the name the display name as elsewhere (the same output path), and a `<details>` "Keys this repository trusts" listing key ids and fingerprints in the groups the creation page uses. A repository that has never had a delivery shows **nothing new** (it still shows the creation snapshot as before; do not invent a sentence). No page says "received", "selected" or "by this server's rule".
- The repository page also says which branch is the project's: "The project's branch is heads/main." (one sentence; the constant of the engine), in a place that does not clutter the page.
- **API:** the repository JSON (`GET /api/v1/repos/{owner}/{name}`) gains an optional `last_delivery` (`delivered_at`, `delivered_by` (display name), `old_tip`, `new_tip`) and `followed_ref`: additive fields, in OpenAPI.

## T3 — wiring
`planeter`'s start-up creates the `DeliveryService` where creation and proposals are wired (it needs the spool and artifact directories: **deliveries are on exactly when proposals are on**; say so in the start-up line, with the archive bound, the stage limits and the deadline, in one line like the other features), runs `reconcile_at_start` before the first request is served, runs `sweep_expired` on the existing periodic sweep, and prints the counters at stop in the existing style. Without the spool: no routes (the ordinary not-found), as for proposals.

## T4 — messages (English written by you; the Japanese plain, by you, flagged for the owner; no 保持, no 預かる; use the glossary)
Every state and every reason of the closed lists has a `message` and a `hint`; the page line and the keys `<details>`. The English texts of the three sentences the owner accepted are fixed (RFC D-4): the line above, and the maintainer's **"Delivering replaces this repository's branch {ref} with yours. It is accepted only if yours continues from the current one; nothing is signed by this server."** — which belongs to the **acceptable** report's `message` (it is what the client will show before asking). Refusal sentences, one per reason, say what is wrong **and what to do** (for example `older_or_diverged`: "Your branch does not continue from this repository's branch. Update your repository from the project's branch, then deliver again."; `unadopted_key`: "Some of your history is signed by a key this repository does not trust. Only the keys listed here can deliver."; `branch_missing`: "This repository has a branch your delivery does not have ({ref}). A delivery may add branches but never remove one."). Nothing mentions *stage*, *chain*, *tip*, *adopt*, *received* or *claim*: a test scans every message of the feature in both languages (as the review view's does). New messages go through the usual route; the sheet is regenerated and `--check`ed; report the count to read.

## T5 — the proofs on the real server process
Using the transport tests' harness for a real `planeter` binary (as `changes_real_server.rs` and `client_e2e.rs` do: real bubblewrap when available, a spool, a seeded token, the TLS terminator only if the harness needs it), and the **real prikk 0.57.0**:
- the whole road over HTTP with `curl`-level requests (no client): upload, view, confirm, polling, the final state; the same for each refusal of the measurement (every archive, S0 and S1: the closed reasons over HTTP, the live tree hash unchanged);
- **SIGKILL of the server process** at: during the stage; after the report; after the intent; **inside the two-rename window** (a test hook or a wrapper that stops the process there; say how); in `exchanged`; in the first, a middle and the last re-accept; before `done`; then **restart** the same binary on the same data and assert as the engine's kill tests do (the repository ends in the new state with every open proposal intact, or in the old state with the stage discarded; `verify` ok; no flag; the delivery final) **and that the API answers consistently** (`GET` of the delivery after the restart; the proposals' pages);
- the window: while a confirm re-accepts (a held lease), `GET` the repository page and a read route: they answer (reads never wait for the W lease: confirm that; if they do not, say what they do);
- a delivery while an accept and while another delivery run (409 `busy`, no half state);
- authorization table cases over HTTP (above) and the 404 equality;
- the 0.7.0 changes view of a **landed** revision after a delivery keeps answering its existing `409 claim_not_held` (handoff 4 improves it, not this one);
- the canary: the whole server log of a run that delivers, refuses and is killed holds no file, branch or key name and no content.
Mutations (each shown failing once): the confirm run attached to the request (a dropped connection aborts it) → the detach test fails; the authorization class removed → the table test fails; the report's `proposals_cannot_be_kept` left empty → the test with a removed artifact fails; the page line shown for a repository without a delivery → fails.

## Non-change scope

## Acceptance criteria
T0–T5 with every test and mutation; OpenAPI, the route table and the API contract tests updated and green; every message of the feature in both languages and scanned; the repository page checked by the structural, stylesheet, glossary, plain-words and language-rule tests; the real-server kill table passes; all gates green (fmt, floor, pin, clippy, tests with prikk 0.57.0 and without — mind that the CI runner has **no bubblewrap**: any stand-in-prikk test must run `Sandbox::Unconfined`, and say you checked it — `cargo deny`/`cargo audit` 0 with the pinned tools, ENF-2, doc, msrv, the dry run with a fresh `CARGO_TARGET_DIR`); CI green. Threat-model input (what the routes accept, cost, refuse, never do) in the review request.
