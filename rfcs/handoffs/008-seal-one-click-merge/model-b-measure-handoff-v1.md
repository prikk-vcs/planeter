## Setup (build it once; scripts under `scripts/` in the package, scratch under `.git-exclude/tmp/` or `/tmp`, deleted at the end)
- **The forge's repository:** created the way a person creates it: a maintainer's repository (keys: one **maintainer key M1**, and a second **maintainer key M2**, both adopted at creation; plus an **unadopted key X**), `prikk archive export`, `POST /api/v1/repos/import` and `…/confirm` against the real server (as the T7 script does). So the forge's store holds a local `heads/main` made by `archive import --adopt`.
- **A maintainer's clone** (real `planeter-client clone`), real `prikk`, with M1: commits, seals (`sync seal` or `seal`, whichever the maintainer would use; say which and the cost), `bundle export --ref heads/main --output`.
- **Contributor flows:** a second client directory with only an author key (no maintainer key) proposing through the real `planeter-client propose`.
- **A repository history ladder** for the cost items: small (30 files, 10 blocks), 63 MiB / 100 blocks, and 259 MiB / 100 blocks (as PK-67's R-series), built with prikk, same content for every run.
- Version strings of everything printed in `versions.txt`.

## M1 — what a client gets when the forge's branch is a received ref (**the question that can change the design**)
Do each of (a)–(e) with the history ladder's small and 63 MiB sizes and report, with commands and outputs:
- (a) **Deliver** a sealed history by `prikk bundle import --input <bundle>` into the forge's repository (the forge's own prikk call, as the driver would make it: the sandboxed driver's `bundle_import`, then by hand if the driver has no caller). Report `branch --format json` (refs and kinds), `log --ref heads/main` and `log --ref remotes/heads/main`, `verify --format json`, `doctor`.
- (b) **What `archive export` of that repository contains** (refs, received refs, blocks): list it with `archive verify --format json` and by importing it into a scratch repository.
- (c) **A maintainer's `planeter-client clone`** of that repository (M1 key present on the maintainer's machine): the refs the clone has, the branch checked out, the files in the working tree, the commit the person sees. Then `planeter-client fetch` after a second delivery: what changes, what the client prints.
- (d) **A contributor's `planeter-client clone`** (no maintainer key): same questions. Which files are in the working tree (the creation snapshot, or the delivered tip, or nothing)? Can the contributor reach the delivered tip's files by any supported command (`extract --ref remotes/heads/main` writes files but not a repository: say what it gives; `merge --from` needs a key: say what it says)?
- (e) **A proposal made after a delivery:** a contributor who has fetched proposes a change **on top of the delivered tip** with the real client (`propose`): does the client find a base (the have-list, `sync have` of the forge cannot query a received ref, U-14), does the server accept the artifact, what is the revision's base, and what do the review pages and the 0.7.0 changes view show (against which parent)? Report every refusal and its words.
- **STOP-1:** if no supported route gives a contributor or a maintainer a clone whose working tree and `heads/main` are the **selected** tip (as opposed to the creation snapshot), or the client cannot propose on top of it, stop after M1 and report with the precise failure. The architect then redesigns (for example the forge's clone path serving a different artifact, or the delivery replacing the repository) before any further measurement.

## M2 — reads on a received ref
For the same delivered repository, run each read the server uses (the `ReadService` verbs: `log`, `show`, `tree`, `cat`, `diff`, `verify`, `branch`, `tag`, `status` if used, `extract --ref`, and the file/raw/blame-like routes' underlying verbs) with `--ref remotes/heads/main` and with the equivalent on a local `heads/main` of an identically built repository: table of verb → accepted? → JSON schema identical? → differences (field values, `ref` names, missing fields, errors) → cost (time, RSS, the existing admission class). Include a block id in place of a ref (`--ref <block-id>`) for each verb that accepts it (the old open question of PK-67). List every place in the **server's read code** that assumes `heads/…` (grep, with file:line): this is the work list of "reads pinned to the selected ref".

## M3 — `bundle preview` on 0.57.0 as the pre-import check
For deliveries (a first one, a fast-forward, an already-included one, an older one, a divergent one, an unrelated one, one signed by M2, one signed by the unadopted X): `bundle preview --format json` against the forge's repository **with and without `--ref remotes/heads/main`**: report the class, `import_class`, `import_refusals` (every field, with real examples), whether it names the **signer** of the tip and of every block and ref-state (key id, adopted or not), and what it does **not** report (the 0.58 completion of "every refusal the import can raise": list the refusals the import raised that the preview did not). The question the design needs answered: **can the forge decide "adopted key, fast-forward of the selected tip" from the preview alone, before any write?** Say yes, no or partly, with the cases.

## M4 — cost and size of a delivery
For the ladder (small, 63 MiB/100 blocks, 259 MiB/100 blocks), each with the 1st delivery and the 2nd (one small commit later): `bundle export` (the maintainer: time, RSS, **bundle size** against the store size; there is no delta bundle, so the 2nd bundle is again the whole history: say the size), the upload (the bound `PRIKK_BUNDLE_MAX_BYTES` default and what refusal appears beyond it, in words), `bundle preview`, `bundle import` (time, RSS, VmData, fsyncs by `strace -c` if available), `verify` after it, and the whole path under the sandbox and the `prlimit` ceiling the driver would set (state the ceiling you used; compare with `docs/extract.md`/RFC 011 cost rules: which existing cost class would each fall in). Also the cost of the maintainer's seal for the ladder's 100-block history (the 0.58 `sync seal` caveat, PK-82): the actual figure for a normal round (one commit, one seal).

## M5 — the poisoned cases, and recovery (**STOP-2**)
On a scratch **copy** of the forge's repository for each (never the one used for M1):
- (a) a fast-forward delivery **signed by the unadopted key X**: what `bundle import` does (accepts? refuses?), what `verify` then says (`publication_trust_issues`), what `branch`/`log` show; then **recovery**: `received remove remotes/heads/main` and re-import of the previous retained bundle: the repository's `verify`, `doctor`, `log` and the refs after it equal those before the poisoned import? (diff the outputs; report the unreached objects left and how `doctor` calls them).
- (b) a delivery signed by M2 (adopted) after M1's: accepted; a delivery by M2 **divergent** from M1's tip: the refusal's exact words and exit code; and that the received ref did not move (tree hash of `.prikk` before/after).
- (c) a **rollback** (an older bundle), an **unrelated** history, a bundle for **another ref name** (`heads/dev`: where does it land, does it touch `remotes/heads/main`?), a **truncated** bundle, a bundle with a **flipped byte** (in a block, a patch, a signature), a bundle over the bound, a bundle that is a **format-8 bundle into a format-7 repository** (if reproducible): for each, the refusal id/words, exit code, and that the store is byte-identical afterwards (as the A1 tables of the 0.56 measurement).
- (d) a **revoked key**: if prikk can remove an adopted key (`trust maintainer remove` or similar; say what exists), deliver a bundle signed by it: what happens; and what `verify` says about **earlier** blocks signed by it.
- (e) **concurrency**: a delivery while a `sync accept` runs, and an accept while a delivery runs, and two deliveries at once: the lock behaviour, the refusal words, whether a started operation is ever left half done (tree hash after a SIGKILL at several points of `bundle import`: the intent, `doctor`, recovery by the existing procedure or by `received remove`).
- **STOP-2:** if any poisoned or interrupted delivery leaves the forge's repository in a state from which the **selected tip cannot be restored by a documented prikk command without forcing a rollback**, stop and report: the design must then prevent the import by a staging copy rather than a pre-check.

## M6 — landing and the review view of landed work
After a delivery that contains the patches of an open proposal (accepted earlier through `propose`): (a) `sync pending` before and after (PK-78 says a received sealed history empties it: confirm for a bundle on 0.57), (b) `log --ref remotes/heads/main --format json`: do its blocks carry the patch ids of the proposal (the intersection RFC 005 D-6 uses), `sealed_by`, `parent_block_ids`; (c) what the **existing proposal page and the 0.7.0 changes view** show for that proposal after the delivery (they should say "not listed here" / `claim_not_held`: capture them), (d) can the changes view of a **landed** proposal be produced from the selected tip: `extract --ref <the sealed block of the proposal's last patch>` and `extract --ref <its parent block>` (PK-80 `log` gives `parent_block_ids`): the files of the two points and the difference, for a one-commit and a three-commit proposal; time/RSS; whether `provisional` is true.

## M7 — what the forge's pages and API say today about the repository's branch
List, with file:line, every page and API field that names the default or current branch, the "latest block", the tip, branches and tags, the clone address and the fetch advertisement (`advertise`), and say for each what it would show after a delivery (the creation snapshot `heads/main` or the selected received tip). This is the work list for the pages ("which tip is shown and why"); it changes no text.

## Reporting rules
Every number says which prikk (0.57.0 unless stated) and the load of the host (as in the 0.56 measurement). Tables as above; the decisive output lines quoted, full outputs in a logs directory; a section "What I could not provoke" for anything not reproduced. **Do not fix anything you find in the product**; list it. Close with a one-page **summary for the architect** answering, in this order: (1) can a clone get the selected tip (STOP-1), (2) can the forge decide before importing (M3), (3) can every poisoned or interrupted delivery be undone (STOP-2), (4) which reads work on a received ref without change, (5) what a delivery costs and where the bound bites, (6) how a landed proposal's changes can be shown, (7) anything unexpected.

## Non-change scope
No code, no test, no doc, no version, no floor, no pin, no CHANGELOG; the only files created are the report package and its scripts; the forge used is a scratch one; nothing is tagged or released; no letter to prikk (the architect writes those).

## Acceptance criteria
Every item M1–M7 answered with commands and outputs or marked "could not provoke" with the reason; STOP-1 and STOP-2 explicitly answered (triggered or not); the summary; a clean `git status` of the repository; scratch deleted.

## Required evidence and review-request format
A table per item as above; the summary; the logs directory; the scripts; `versions.txt`; deviations and open questions.
