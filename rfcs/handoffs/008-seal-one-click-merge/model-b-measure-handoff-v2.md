# RFC 008 / RFC 004 D-8 — Landing by successor replacement: measure the new shape (0.8.0 stage 0b) — Implementation Handoff (v2)

| | |
|---|---|
| Document | Stage 0 (`model-b-measure-handoff-v1`) triggered **STOP-1**, correctly and with excellent evidence: with a delivery as a *received ref*, the forge's local `heads/main` never moves, so a clone gets the creation snapshot as `heads/main`, a keyless contributor can never reach the delivered tip, `fetch` breaks, and proposals are made against the stale base (ledger PK-83). **The architect's redesign (D-93): *successor replacement*.** A delivery is a **repository archive** of the maintainer's repository (the same artifact as repository creation). The forge **stages** it in a scratch repository with the repository's adopted keys (prikk itself lets only adopted-key-signed refs land as local branches), applies the written rule to the staged result (the staged `heads/main` must be a **fast-forward successor** of the forge's current `heads/main`, and `verify` passes), and only then makes the delivered state the repository's own `heads/main`. After that the forge's `heads/main` **is** the project's branch: clone, fetch, reads, the proposal base, landing (RFC 005 D-6: the patches are in a block of a *published* ref) and the 0.7.0 changes view all keep working unchanged. There is no "received tip" and no selection beside the branch. This handoff measures **whether that is possible with prikk 0.57.0 and what it costs**. Measurement only, like v1: no repository file changes. |

## Setup
Reuse v1's keys (M1, M2 adopted; X unadopted; C author-only), lineages (small 10 blocks; 63 MiB/100 blocks; 259 MiB/100 blocks) and variants (`div`, `m2`, `m2div`, `x`, `unrelated`, `dev`), the forge stack and the creation of `alice/small` and `alice/big`. The delivery artifact is **`prikk archive export` of the maintainer's whole repository** (D1 = the history up to block 10 / 100; D2 = D1 + one block). Add what v1 did not have: a **forge with open proposals** — `alice/small` with (P1) a proposal whose patches are **in** D1 (so it should land), (P2) a proposal whose patches are **not** in D1 (open, on top of the creation tip), (P3) a three-revision proposal of which only the first is in D1; all made with the real `planeter-client propose` (a contributor with their own maintainer key X, as v1 found the realistic one is).

## Questions (answer all, in this order; each with commands, outputs and a table)
**R1 — staging.** In a scratch repository made the way creation makes the stage (`init`, `trust maintainer add` of the repository's adopted keys, the spool/sandbox as the driver would): (a) `archive verify --format json` of D1 and D2; (b) `archive import --adopt --format json` of D1: the landings (which refs become **local**, which `remotes/`), `verify`, `doctor`, `log heads/main`; time, RSS, VmData at small and 63 MiB (and 259 MiB if cheap); (c) the **poisoned archives** at the stage: D1 signed by the unadopted key X (variant `x`), an archive whose `heads/main` is signed by M2 but a block by X, an **older** archive (rollback), a **divergent** one (`div`, `m2div`), an **unrelated** one, `dev` (another ref name only), a truncated one, a flipped byte (block, patch, signature), an archive over the bound, an archive naming a **key the forge has not adopted** in its carried keys: for each, what lands where, what `archive verify` and the import say (exact words and exit codes) and the answer to the one question that matters: **can the forge tell from the stage's own output that "every ref that would become the repository's published ref is signed by an adopted key and is a fast-forward of the current one"?** If the stage's `log heads/main --format json` can answer the fast-forward question (the current tip block id appears in the staged chain), give the exact fields.
**R2 — the rule on the stage.** From the staged repository decide, with the driver's existing readers only, for D1 and each poisoned variant: (i) every local ref, its tip, signer(s) (`log --format json` `sealed_by`, `verify` `publication_trust_issues`, `block_seals`); (ii) whether the **forge's current `heads/main` tip block id** is in the staged `heads/main` history; (iii) whether the staged repository has any published ref that the live one lacks (`dev`) or lacks one the live one has (a deleted branch): report each case. Decision input for the RFC: which of these the rule should refuse.
**R3 — putting the staged state under the live repository's `heads/main`.** The live repository has local `heads/main` (the creation snapshot or an earlier delivery), **pending claims and patches of open proposals**, tags maybe, and the forge's lease/intent/recovery machinery. Measure both mechanisms, on copies of the live repository:
 - **R3a — advance in place:** can a keyless process remove the live `heads/main` (`branch delete`? `received remove` is for received refs; say what exists and what it demands, e.g. a signing key) and then `archive import --adopt` the delivery into the **live** repository so that `heads/main` lands as a local branch (PK-34: absent refs land local)? Report each command, its words, exit code, whether any step needs a key, the state after each step (refs, `verify`, `sync pending`, tree hash of `.prikk`), and the window in which the repository has no `heads/main` (what a read, a clone export, an accept would do in that window).
 - **R3b — replace the repository:** the staged repository becomes the live one (directory rename under the write lease, the old one kept as the previous generation), and **the open proposals' retained artifacts are accepted again** (P2, P3 from the artifact store, in revision order, with the driver's `sync accept`): report whether the re-accept succeeds (claims whose parent is an ancestor of the new tip; claims of patches that are already sealed in D1: refused, no-op, or fine), what `sync pending` shows afterwards for P1/P2/P3, the time per patch (about 10 fsyncs per patch, PK-82) for the three proposals and for a 1,000-patch revision, and the changes view (0.7.0) of P2 and P3 afterwards.
 - **State which of R3a/R3b works, which is simpler, and any result that needs a key.** **STOP-3:** if neither can be done without a signing key or without losing the pending claims of open proposals, stop and report.
**R4 — crash safety of the chosen mechanism(s).** SIGKILL at each step of the sequence (stage import; the rule; the removal; the import; the rename; each re-accept) at several points; after each, what the repository is, what `verify`/`doctor` say, whether the forge can **complete** the delivery from what it has (the retained archive) or **return to the previous state** with documented prikk commands or a rename back; and what a reader sees during the sequence (lease behaviour: a read, `fetch`, an accept during a delivery; a delivery during an accept). **STOP-4:** a kill that leaves the repository unrecoverable or silently different from both the old and the new state.
**R5 — what people get after a replacement.** (a) a fresh `planeter-client clone` by a maintainer and by a contributor (own key X): `heads/main` and the working tree are the **delivered** tip; `prikk status`; no `remotes/` copy; (b) a contributor proposes on top of it: the base, the revision, the 0.7.0 changes view's `compared`; (c) **`planeter-client fetch` in a clone made before the delivery**: what lands (the new tip as a received copy, as `fetch` always does: say exactly), the exit code, the printed words, the state of the clone's `heads/main`, and what a maintainer does next to move forward (`merge --from`: its result and whether the resulting `heads/main` block equals the forge's or is a new block as v1 found); the same for a contributor with a key of their own; (d) the forge's advertisement (`advertise`) and the `fetch` offer after the replacement; (e) `clone` right after the replacement and after a second one (D2).
**R6 — landing and the view of landed work.** For P1/P2/P3 after the replacement: `sync pending`, `log heads/main` patch ids, what the **existing landing observation** and the proposal page say (does P1 show Landed and P2/P3 stay open with the right counts?), what the 0.7.0 changes view says for P1 (`claim_not_held`, as v1 showed for a similar case) and whether a view of a landed proposal can be produced from the sealed history: `extract --ref <block>` of the proposal's last sealed block and of its parent (find them from `log heads/main --format json`: `patch_messages[].patch_id`, `parent_block_ids`), for a one-commit and a three-commit proposal; time/RSS; `provisional`.
**R7 — cost and size.** For the ladder: the maintainer's `archive export` (time, RSS, **size**; the whole history every time), the upload bounds that apply (the creation stage budget and size bound in the server: read them from the code, state the numbers and the refusal words beyond them), the stage import, `verify`, the replacement itself, the re-accept of open proposals, and the total time the repository is under the write lease (the window reads and accepts wait or fail). State which existing admission cost class each step falls in (RFC 011) and what memory ceiling the sandbox needs.
**R8 — the pages and API that name the branch (v1's M7, now short).** List, with file:line, every page and API field that names the branch, tip, the clone address, `advertise`: with a replacement they all keep working; say if any of them would show something wrong, stale or misleading after one (a cache, the state fingerprint/ETag, the `history` page, counters). Say how the fingerprint moves at a replacement.

## STOP rules
STOP-3 and STOP-4 above; plus **STOP-5:** if any poisoned archive of R1(c) lands as the live `heads/main` (or would, in the sequence you measured), stop and report: the rule would then not be enforceable from prikk's own output.

## Reporting rules
As v1: every number says the prikk version and the host load; the decisive lines quoted; full outputs in a logs directory; "what I could not provoke". **Do not fix anything you find; list it.** Close with a **one-page summary**: (1) can a poisoned or older/divergent archive ever become the live branch (R1, R2)? (2) which mechanism installs a delivery (R3) and does it keep the open proposals? (3) can every interrupted delivery be completed or undone (R4)? (4) what a clone, a fetch and a proposal look like afterwards (R5)? (5) does landing work with the existing code, and how is the view of landed work produced (R6)? (6) cost, size, lease window (R7)? (7) anything unexpected, including every limitation of prikk 0.57 that the design must state to users.

## Non-change scope
No code, test, doc, version, floor, pin or CHANGELOG; the only files created are the report package and its scripts; scratch forges only; nothing tagged or released; no letter to prikk.

## Acceptance criteria
R1–R8 answered or marked "could not provoke" with the reason; the three STOP rules explicitly answered; the summary; a clean `git status`; scratch deleted.

## Required evidence and review-request format
A table per question; the summary; the logs directory and scripts; `versions.txt`; deviations and open questions.
