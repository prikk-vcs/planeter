# RFC 005 — Change review — Implementation Handoff (v2, part 6): comments and review decisions

| | |
|---|---|
| Document | Part 6 of the RFC 005 v2 series: **people talk about a proposal and say what they think of a revision** (RFC 005 D-5): comments in threads, anchored to a patch (and optionally a path and lines), and one decision per reviewer per revision — *approve* or *request changes* — that is shown on the revision it was given for and **never carried over** to a later one. Then the default view may truthfully show a review state (D-11), which part 5 deliberately left out. No file-by-file view (blocked on prikk: see "Not here"), no checks, no merge. |
| Status | **Assigned** (2026-10-27), after part 5a was reviewed Approved. Independent of the supply-chain decision and of the client helper. |
| Basis | [`../../accepted/005-change-review.md`](../../accepted/005-change-review.md) D-5, D-7 (stale never counts), D-10, D-11; `docs/proposals.md`; `crates/planeter-core/src/authorize.rs` (`Action::Comment`: any authenticated principal who can read the repository, a read-only token included; `Action::Review`: `write` and above; `Action::Close`); `crates/planeter-core/src/change.rs` (`approval_standing`, `Staleness`); part 5's service, routes, pages, catalog, WCAG checker, plain-words tests, glossary; RFC 003's Markdown sanitizer; the route registry (IS-14). |
| Audience | Dev team. Return a review-request package (`.git-exclude/review-requests/`). |

## Change scope

- **T1 — Records (both store implementations, one shared suite; an idempotent migration; internal names stay `change`).** `comments`: id, proposal, revision seq the author saw, optional `patch_id` (must be in the proposal's patch set *at the time*; kept as written), optional `path` (≤ 1,024 characters, free text, never opened), optional `line_from`/`line_to` (positive, `from ≤ to`), optional parent comment (a thread is one level deep: a reply's parent must itself be a top-level comment of the same proposal), author, body (Markdown source ≤ 16 KiB, non-empty after trimming), created_at, and a moderation record (`hidden_by`, `hidden_reason`, `hidden_at`, all or none). **Comments are immutable and never deleted**: no edit, no delete by the author (a typo is a new reply). `decisions`: proposal, revision seq, reviewer, `approve | request-changes`, optional note (≤ 2 KiB, plain text), created_at; **one current decision per (reviewer, revision)**, replaced by recording a new one (the superseded one stays in a history table, newest wins). Database-enforced uniqueness and CHECKs as in part 3a; tests with injected failure; a migration test from the part 5 schema over three reopens.
- **T2 — Rules (pure, in `planeter-core`, exhaustively tested).** (a) **Who may add what:** a comment needs `authorize(Comment)`; a decision needs `authorize(Review)`; both need the proposal to be readable by the caller. (b) **State:** comments are accepted on `open` proposals and — for discussion after the fact — on `landed`/`closed` ones for **the same people**, up to 30 days after the change of state (the grace of the retention); decisions only while `open`. (c) **No self-approval:** the submitter of a revision cannot record `approve` on it (a named refusal; `request-changes` and comments are allowed); a person who submitted *any* revision of the proposal cannot approve the **proposal's** latest revision either. (d) **A decision belongs to one revision** (default: the latest; naming an older revision is refused `revision_not_current`): `approval_standing(approved_on_seq, current_seq)` decides what later revisions show — "approved on revision 1" is shown on revision 2 and **never counts** toward the current revision (D-7). (e) **The review state of a proposal** is a pure function of the current decisions on the **latest** revision: `changes_requested` if any reviewer's current decision on it is `request-changes`; else `approved` if at least one is `approve`; else `awaiting_review`. Earlier-revision decisions are history, shown separately. Counts are of distinct reviewers. (f) **Hiding:** `RepoAdmin` may hide a comment with a reason (≤ 500 characters); a hidden comment shows "hidden by a maintainer: *reason*" to everyone and its body to nobody but `RepoAdmin` (and the API says `hidden: true` without the body for others); hiding is recorded, reversible by `RepoAdmin`, and is the only moderation in this part.
- **T3 — API (bearer-only for writes, like `close`; reads follow the proposal's read gate).** `POST …/proposals/{id}/comments` `{body, patch_id?, path?, line_from?, line_to?, parent?}`; `POST …/proposals/{id}/decisions` `{decision, note?, revision?}`; `POST …/proposals/{id}/comments/{cid}/hide` `{reason}` and `…/unhide`. `GET …/proposals/{id}` gains `review` (state, counts, the current decisions with reviewer names, history of earlier revisions' decisions as `approved_on` / `requested_changes_on` lists) and `comments` (paged, oldest first, `limit` ≤ 100, `after` cursor; replies nested under their parent; body as source and as sanitized HTML; hidden handling as above). Rate limits **per principal per proposal**: 20 comments an hour, 10 decisions an hour (operator variables; refusals `429` with `Retry-After`); the existing per-caller edge limits stay. Existence-neutral 404 for hidden repositories and unknown ids; named refusals for each rule of T2 with catalog sentences; OpenAPI and its drift guard; one error shape; IS-14 rows (`Authorized(Comment)`, `Authorized(Review)`, `Authorized(RepoAdmin)`).
- **T4 — Pages.** On the proposal page: the default view gains **one review line** — *Awaiting review*, *Approved by 2 people*, or *Changes requested by 1 person* — with its plain meaning in a sentence ("Approved here means reviewers said they are happy with revision 3. It does not merge anything."), and a note when the only approvals were for an earlier revision ("Approved on an earlier revision; revision 3 has not been reviewed."). Everything else under **Details**: the decisions (who, which revision, note), the thread of comments with their anchors ("on patch `abcd…`, `path:12–14`"), the forms the viewer may use (comment: any signed-in reader; decision: reviewers; each form states its consequence beside the button; CSRF as for close; hide/unhide for `RepoAdmin`). No script required; keyboard reachable; the 17 structural rules, the plain-words and stylesheet tests, both languages; diff-like colouring is not used here. The repository's proposal **list** shows a small review word per row (the same three words).
- **T5 — Words.** Glossary rows (drafted for the architect's approval; flagged for the owner): *comment*, *review*, *approve*, *request changes*, *hide*. Catalog messages in both languages; Japanese draft rows in an addendum for the reviewers (a dedicated word for *approve* and *request changes* is the reviewers' to decide). The retired-words test keeps "approved" **out of any sentence about a proposal that is not about a reviewer's decision** (planted case: "Approved, awaiting signature" next to a proposal fails — it stays out of this part because the owner is asked about it).
- **T6 — Documentation and tests.** `docs/proposals.md` (review, comments, moderation, the rules of T2 as a table); CHANGELOG; STATUS. Tests: every rule of T2 with a negative; **the stale approval** (approve revision 1, record revision 2: the review line says "Approved on an earlier revision", the state is `awaiting_review`, the API shows `approved_on: [1]`); the self-approval refusals; a read-only token may comment but cannot decide; an anonymous reader sees comments and no forms; a hidden comment's body never appears for a non-admin in HTML or JSON; HTML-looking bodies are sanitized (a `<script>` and an `onerror` attribute are gone); a comment anchored to a patch not in the set is refused; the thread depth rule; rate limits; concurrency (two reviewers deciding at once; the same reviewer twice at once → one current decision); the kill case is not applicable (no prikk call writes here).

## Not here (decided, held)

The **file-by-file view** (RFC 005 D-4): `extract --claim` refuses a claim whose parent is itself a pending claim (prikk 0.54.1 reports it as `damaged-repository`; 0.55.0 will name it), so a proposal of several commits can show only its first step; the architect is asking prikk whether a chain of pending claims can be materialized. The view is written after the answer. Likewise **checks/CI status** (RFC 006), **merge/publication** (D-8), **notifications**, **suggested changes**, **resolved/unresolved threads**, **editing comments** — each its own RFC or a decision to add (Q-1).
The owner-approved badge "Approved, awaiting signature" and `explain.queued` are untouched here.

## Non-change scope

No change to `propose`, landing, recovery, the quotas or retention; no new dependency; no `unsafe`; no version or release change.

## Acceptance criteria

T1–T6 as written; the IS-14 table, OpenAPI drift guard, ENF-2 and every earlier check pass; both supply-chain gates are reported as they are on a fresh database (they may be red while IS-54 is open; say so); every other gate green, both test runs named, `cargo doc`; the pages pass the structural checker and the plain-words tests in both languages with zero violations.

## Prohibited shortcuts

No approval carried to a later revision; no count of a stale approval; no edit or delete of a comment; no hidden body for a non-admin anywhere (HTML, JSON, logs); no state computed from anything but the decisions of T2(e); no hard-coded user-visible text; no hidden/absent/denied difference that a stranger can see.

## Required evidence and review-request format

Commits (hash → what, by task); the rules table with a test per row; API transcripts (comment, reply, decision, replacement, stale approval, hide/unhide, each refusal); the HTML (default view and Details) in both languages with the checker's result; the concurrency tests; the glossary rows drafted; every gate with command and exit code and the advisory-database HEAD; deviations and open questions.
