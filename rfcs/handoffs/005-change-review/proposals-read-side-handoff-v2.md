## T0 — Vocabulary: *proposal* (first; user-visible and API names only; the internal `change` names stay)

Decided (D-38): the thing a person proposes is a **proposal**; its versions are **revisions**; *change* keeps its glossary meaning (a recorded unit of history). Nothing is released, so the rename is free now and impossible later.
Rename, in code, catalog (both languages), OpenAPI, tests and docs: the propose request's metadata field `change` → `proposal`; the propose response's `change_id` → `proposal_id` and `created_change` → `created_proposal`; error codes
`unknown_change`/`change_not_open`/`not_your_change` → `unknown_proposal`/`proposal_not_open`/`not_your_proposal` (catalog keys follow); every English and Japanese sentence that says *change* for a proposal (the eight `quota.*` texts, `error.*` texts, `propose.*`, `recovery.*` that say "open changes",
"a change") says *proposal* (Japanese 提案, which the draft already uses for *propose*; the reviewers' addenda get a **replacement addendum 6** listing each reworded row by key, and the withdrawn keys are named); `docs/changes.md` is renamed `docs/proposals.md` (links updated) and says at its top that the code's internal name for a proposal is *change*.
**Keep** the internal Rust/SQL names (`ChangeRecord`, `changes`, `ChangeStore`, `change_id` columns): a doc comment at each public type says "a *proposal* in the product's words". The glossary gets rows (drafted by you, **approved by the architect before merge**, and flagged for the owner, who approved the glossary): *proposal*, *revision*, *landed*, *held for review*, *built on*. The retired-words test gains "change" **only** where it means a proposal (a planted case: "open changes" fails; "a recorded change" in the history pages passes).

## Change scope

- **T1 — Landing, observed from facts (RFC 005 D-6, clarified by the architect).** A proposal is `landed` only when **every** patch id of its current patch set (`current_patch_set`) is **absent from `sync pending` and present in a block that `log` lists for a ref the repository holds** (published or received). Absent-from-pending alone is not enough (a patch that merely disappeared would be a false "landed"). Cost control: one `sync pending` per repository per state fingerprint, shared by all open proposals of that repository, in memory; `log` is read **only when some proposal's patches have all left pending** (candidates), and the patch-ids of sealed blocks found are not re-read for the same fingerprint. The transition is persisted with `transition(...)` as a **compare-and-set** (the proposal is still open and its revision count is the one observed; a revision recorded meanwhile wins and the observation is discarded). Test with a stand-in prikk and with the real one (a maintainer's local seal received by `archive import` into a test repository).
  The page and API must not claim what cannot happen: until the owner's D-8 decision is built, what happens after a maintainer signs the work is not settled, so the page says only what is true under every answer, in one plain sentence where the state is shown: "This server does not merge anything itself; a maintainer signs the work on their own computer." (the architect revises the sentence when D-8 is built).
- **T2 — The read API.** `GET /api/v1/repos/{owner}/{name}/proposals` (list; filter `state=open|landed|closed|all` default `open`; newest-updated first; bounded page, `limit` ≤ 100, `after` cursor; per item: id, title, state, opened by, opened/updated times, revision count, patch count of the current set, `built_on` presence, and for landed/closed the artifact-retention state) and `GET …/proposals/{id}` (detail: title, description (rendered Markdown through the RFC 003 sanitizer, and the source), state with its reason or its landing observation, the revisions in order — each with seq, time, submitter, claims with their outcomes **as accept reported them (stored, not re-asserted)**, key ids, the *built-on* base (D-3's "declared base", worded for people), the declared/undeclared note of D-1, added count, artifact digest and size, `artifact_available` — and the patches of the **current** set, at most 1,000 listed with a `truncated` flag, each with the `Assurance` from `patch_assurance` computed from facts of the same observation, never from `queued`). Both: `Authorized(Read)` through the route registry (hidden or absent repository: identical 404; IS-14 rows), existence-neutral for ids; the OpenAPI drift guard; one error shape; rate limited like the fetch routes. No prikk call per list item.
- **T3 — Closing.** `POST …/proposals/{id}/close` with `{reason}` (required, ≤ 1,000 characters): allowed to **the proposal's opener** and to principals for whom `authorize(Close)` allows; a landed or closed proposal answers a named refusal (`TransitionError::AlreadyFinal`, `ReasonRequired` mapped to API codes and catalog sentences); on success `retain_until = now + grace` (operator variable, default 30 days). The UI form is CSRF-protected the way the project's other forms are; the API is bearer-only (no cookie), like `propose`. The page states the consequence beside the button ("Closing keeps the record and the files; nobody can reopen it."), per D-11 "no action whose consequence the page does not state".
- **T4 — Pages.** `/{owner}/{repo}/proposals` and `/{owner}/{repo}/proposals/{id}`, in the existing layout, nav and catalog (English and the Japanese draft), WCAG-2.2-AA structural checker rules, stylesheet tests, plain-words tests, keyboard-only reachable, no script required. **Default view (D-11) shows only:** the title, who proposed it, the state (*Open*, *Landed*, *Closed*), one sentence of what it is ("Held for review: not yet part of the project's history."), a one-line summary ("3 patches in 2 revisions"), and the actions the viewer may take. **Everything else under `<details>` "Details":** revisions, the patches with their assurance badges (the existing badge and explanation machinery), the claims and signature outcomes, key ids, the built-on base, retained artifact digests. The review-state and checks lines of D-11 are **not shown** in this part (they would be statements about things that do not exist yet). Where the file-by-file view will be, the page says plainly "The file-by-file view is not available yet." (D-4.1). The repository nav shows *Proposals* only when the repository has at least one or the viewer may propose; the home/repo page shows the number of open ones, nothing more. Titles are escaped; descriptions go through the sanitizer; submitter names are the account names already shown elsewhere.
- **T5 — Download of an accepted artifact (D-8).** `GET …/proposals/{id}/revisions/{seq}/artifact`, for principals who hold **`review` or `merge-seal`** (either). The route registry gets a variant `AuthorizedAny(&[Action])` (the architect authorizes this one addition; the IS-14 table lists both actions); a caller who cannot read the repository gets the neutral 404, one who can read but holds neither gets 403. Served from the artifact store with the fetch route's machinery (`Range`, `ETag` = the digest, `Accept-Ranges`, `Content-Length`, the same rate limits and per-host concurrency, never under a repository lease: the file is immutable); content type `application/octet-stream`; `Content-Disposition` with a safe generated name (`<repo>-proposal-<id>-r<seq>.prikk-sync`). After retention the artifact may be gone: `410` with the plain sentence and the date it was removed. The page shows the download only to those who may.
- **T6 — Retention sweep.** `ArtifactStore::remove(digest)` (new; the store "never deletes" today): rename into a trash name then unlink, so a kill leaves nothing half-removed, and start-up clears the trash. A sweep (at start and hourly, one at a time, bounded work per run) removes an artifact only when **every** revision that names its digest belongs to a proposal that is `landed` or `closed` with `retain_until` in the past, **and** no open intent names it, **and** no open proposal does. Records stay (the revision keeps digest and size; `artifact_available` is derived from the store). Counters and one log line per run. Tests: shared digest (two proposals), an open intent holding the artifact, the grace boundary (inclusive), a kill between rename and unlink, a revision whose file is already gone.
- **T7 — Documentation and messages.** `docs/proposals.md` (model, states, landing rule, retention, the API, the pages, the download), the OpenAPI text, CHANGELOG, STATUS; every new text a catalog message with Japanese draft rows in the **replacement addendum 6** (T0) and a **seventh** for the new pages if you prefer two files; the architect updates the threat model.

## Non-change scope

No comments, threads or decisions (part 6); no checks or CI status; no file-level or diff view (prikk 0.54.0, RFC 006 v2); no seal, merge or publication; no change to the propose route's framing, check order or quotas beyond T0's names; no new dependency; no `unsafe`; no version or release change.

## Acceptance criteria

T0's rename is complete (a grep for the old API names finds only history, the RFC's note and the reviewers' withdrawn-key list) and the glossary rows are drafted; with real prikk a proposal made by `propose` appears in the list and the detail (JSON and pages), a second revision appears in order, an undeclared push is labelled as such, pending patches show as held and never as signed, closing works for the opener and for `Close`, refuses a stranger and a reader, and keeps the record; a received sealed history makes the proposal `landed` only when every patch is in a listed block and none is pending, and a patch merely removed from pending does not; the download is byte-identical to what was proposed, resumes with `Range`, is refused to a reader who holds neither `review` nor `merge-seal`, and is `410` after the sweep; the sweep keeps what it must (the five tests of T6); every page passes the WCAG checker and the plain-words tests in both languages; the IS-14 table, the OpenAPI drift guard, ENF-2 and every earlier check pass; every gate green including both supply-chain gates (fresh advisory database), both test runs named, `cargo doc`.

## Prohibited shortcuts

No `landed` from absence in `sync pending` alone; no assurance from `queued`; no prikk call per list item; no page or API that shows a review or checks state that does not exist; no hard-coded user-visible text outside the catalog; no hidden/absent/denied difference a stranger can see; no deletion of an artifact still named by an open intent or an open proposal; no rename of the internal storage names in this part.

## Known risks

The vocabulary change touches many files: do it as its own commits, mechanically, with the old names grep-checked to zero before T1. `log` of a large repository is the expensive read: the candidate rule of T1 exists to keep it rare; measure the observation on a repository with 5,000 pending patches and 200 sealed blocks and report it. The detail page's patch list is bounded (1,000) so a proposal cannot make the page unbounded.

## Required evidence and review-request format

Commits (hash → what, by task; T0's mechanical commits listed separately); the grep for the old names; screenshots-as-text are not required, but the HTML of the list and the detail page of a real proposal (default view and Details) in both languages, with the checker's result; the landing tests including the negative one; the API transcripts (list, detail, close, download with Range, 410); the sweep tests; the observation timing; the glossary rows drafted; every gate with command and exit code and the advisory-database HEAD; deviations and open questions.
